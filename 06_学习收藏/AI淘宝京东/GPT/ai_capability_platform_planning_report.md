# AI 能力交易平台整体规划报告

**项目主题**：面向 AI Agent 的 AI 能力交易平台  
**核心定位**：让 AI Agent 像企业采购员一样，自动发现、比较、购买、组合、调用并反馈 AI 能力。  
**报告版本**：V1.0  
**撰写日期**：2026-06-06  
**适用对象**：创始团队、产品团队、技术团队、运营团队、融资材料、战略路线图

---

## 0. 总体结论

本项目不应被规划为“AI 工具商城”，而应规划为：

> **AI 能力交易网络：面向人类与 AI Agent 的双界面平台。人类负责预算、授权、风控和验收；AI Agent 负责自动搜索、比较、调用、组合和反馈。**

平台的长期价值不是“上架了多少 AI 工具”，而是：

1. 是否建立了统一的能力商品标准；
2. 是否能让 AI Agent 自动理解和调用能力；
3. 是否能完成交易、结算、履约和评价闭环；
4. 是否能沉淀真实效果数据；
5. 是否能建立跨模型、跨云、跨服务商的中立信任网络。

## 1. 战略定位

### 1.1 项目使命

> **让 AI 能力像商品一样流通，让 AI Agent 像采购员一样调用世界上的外部能力。**

### 1.2 项目愿景

未来，每个企业都会有多个 AI Agent：客服 Agent、销售 Agent、财务 Agent、法务 Agent、运营 Agent、研发 Agent、采购 Agent。这些 Agent 不可能自己拥有所有能力，而是需要像企业员工采购软件和服务一样，从外部能力市场寻找能力。

本平台要成为：

> **AI Agent 采购外部能力的默认入口。**

### 1.3 项目定位

更准确的定位是：

> **面向 AI Agent 的能力采购、调用、组合、结算与信任平台。**

对人类，它像一个 AI 版淘宝 / 天猫 / 服务市场。  
对 AI，它是一个可读、可调、可交易、可审计的能力协议层。  
对商家，它是一个 AI 能力变现平台。  
对企业，它是一个可治理的 AI 能力采购系统。

### 1.4 核心口号

可用于不同场景：

- **AI 时代的能力交易所。**
- **让 AI 能力像商品一样流通。**
- **交易的不是工具，而是能力。**
- **人类看商城，AI 读协议。**
- **让 AI Agent 自动发现、比较、购买、组合并执行 AI 能力。**

### 1.5 战略边界

平台不做：

- 不自研所有 AI 产品；
- 不自营所有模型；
- 不一开始重资产做算力；
- 不做简单工具导航；
- 不一开始完全开放所有商家；
- 不把自己绑定在单一模型生态里。

平台要做：

- 做能力标准；
- 做商家和商品体系；
- 做 Agent 可调用接口；
- 做交易和结算；
- 做评价和评测；
- 做担保和仲裁；
- 做权限和安全；
- 做组合和调度；
- 做数据闭环。

## 5. 能力卡片标准设计

### 5.1 为什么能力卡片是核心

淘宝商品页是给人看的；AI 能力卡片必须同时给人和 AI 看。

能力卡片要解决：

- 这个能力能做什么；
- 输入是什么；
- 输出是什么；
- 怎么调用；
- 多少钱；
- 多快；
- 多准；
- 风险是什么；
- 数据怎么处理；
- 是否可组合；
- 出错谁负责。

### 5.2 能力卡片字段总表

| 模块 | 字段 |
|---|---|
| 基础信息 | 名称、分类、商家、版本、状态、标签、适用行业 |
| 业务描述 | 解决问题、适合客户、典型场景、不适用场景 |
| 输入输出 | input_schema、output_schema、文件类型、最大输入限制 |
| 调用接口 | API、MCP、SDK、Webhook、认证方式、限流 |
| 价格模型 | 按次、按量、订阅、项目制、套餐、免费试用 |
| SLA | 可用性、平均延迟、P95 延迟、响应时间、支持时间 |
| 质量指标 | 成功率、准确率、人工通过率、投诉率、复购率 |
| 安全合规 | 数据保留、是否训练、是否脱敏、私有部署、审计日志 |
| 风险等级 | 低、中、高、强监管、是否需要人工审批 |
| 组合关系 | 依赖能力、可接入能力、前置条件、输出兼容性 |
| 交付规则 | 交付周期、验收方式、里程碑、售后周期 |
| 责任边界 | 失败赔付、退款规则、免责声明、商家责任 |
| 评价数据 | 用户评分、Agent 评分、真实调用数据、平台评测 |

## 6. AI Agent 调用体系设计

### 6.1 Agent 访问平台的完整流程

```text
1. Agent 接收任务
2. Agent 拆解需求
3. 调用平台搜索 API
4. 获取候选能力列表
5. 读取能力卡片
6. 根据预算、质量、风险、SLA 排序
7. 请求试用或报价
8. 生成组合方案
9. 请求人类审批或自动下单
10. 调用能力执行任务
11. 接收结果
12. 记录日志
13. 提交评价与反馈
```

### 6.2 Agent API 设计

#### 6.2.1 搜索能力

```http
POST /v1/capabilities/search
```

请求示例：

```json
{
  "task": "为一家电商公司搭建 AI 客服知识库",

  "deadline_days": 7,
  "constraints": {
    "data_region": "CN",

    "requires_wechat_work": true

  "agent_context": {
    "organization_id": "org_123",
    "permission_level": "recommend_only"
  }
}
```

返回示例：

```json
{
  "results": [
    {
      "capability_id": "pkg_ai_customer_service_001",
      "match_score": 0.91,
      "estimated_price_cny": 18000,
      "risk_level": "medium",
      "recommended_reason": "支持企业微信，交付周期 7 天，已有电商案例"
    }
  ]
}
```

#### 6.2.2 读取能力详情

```http
GET /v1/capabilities/{capability_id}
```

返回 Capability Card 完整结构。

#### 6.2.3 获取报价

```http
POST /v1/quotes
```

适用于非固定价格商品，如专家服务、方案包、私有部署。

#### 6.2.4 发起试用

```http
POST /v1/trials
```

适用于 API、Agent、模型能力。

#### 6.2.5 创建订单

```http
POST /v1/orders
```

订单创建需要检查：

- Agent 是否有权限；
- 预算是否足够；
- 风险等级是否需要人工审批；
- 数据是否符合安全规则；
- 该商品是否允许自动下单。

#### 6.2.6 执行能力

```http
POST /v1/execute
```

适用于可直接调用能力。

#### 6.2.7 提交反馈

```http
POST /v1/feedback
```

反馈包括：

- 任务是否完成；
- 输出是否通过验收；
- 成本是否符合预期；
- 延迟是否达标；
- 是否产生错误；
- 用户满意度。

### 6.4 Agent 权限等级

平台必须设计 Agent 权限等级，不能一开始允许所有 Agent 自动付款。

| 等级 | 名称 | 权限 |
|---|---|---|
| L0 | 只读 | 可搜索、读取能力卡片，不可试用、不可下单 |
| L1 | 可试用 | 可调用免费试用或沙箱，不可付费 |
| L2 | 建议采购 | 可生成采购建议，需人类确认 |
| L3 | 小额自动采购 | 可在预算内自动购买低风险能力 |
| L4 | 受控自主采购 | 可自动组合、下单、调用，但有审计与回滚 |
| L5 | 完全自主 | 暂不建议早期开放，仅限高度受控环境 |

建议 MVP 支持 L0-L3 即可。

### 6.5 人类审批机制

触发人工审批的条件：

- 单笔金额超过阈值；
- 涉及敏感数据；
- 商品风险等级为高；
- 需要专家服务；
- 需要私有部署；
- 首次调用某商家；
- Agent 异常行为；
- 预算即将耗尽。

审批结果应回传给 Agent：

```json
{
  "approval_status": "approved",
  "approved_by": "user_789",
  "budget_limit_cny": 5000,
  "allowed_actions": ["trial", "execute", "monthly_subscription"]
}
```

## 7. 搜索、匹配与推荐系统

### 7.1 搜索不是关键词搜索，而是任务匹配

人类可能搜索：

```text
AI 客服
企业知识库
合同审查
```

AI Agent 更可能提交结构化任务：

```json
{
  "goal": "搭建售后客服机器人",
  "constraints": {
    "budget": 30000,
    "deadline": "7 days",
    "platform": "企业微信",
    "data_policy": "数据不出境"
  }
}
```

平台搜索系统需要同时支持：

- 关键词搜索；
- 语义搜索；
- 结构化过滤；
- 任务拆解；
- 能力图谱匹配；
- 质量排序；
- 风险过滤；
- 预算优化。

### 7.2 推荐排序因子

建议排序公式考虑：

```text
综合得分 = 任务匹配度 * 30%
        + 质量评分 * 20%
        + 成本效率 * 15%
        + 稳定性 * 10%
        + 交付可靠性 * 10%
        + 安全合规 * 10%
        + 平台战略因子 * 5%
```

注意：商业广告不应直接干预 AI 自动推荐的核心排序。

### 7.3 任务拆解引擎

任务拆解引擎用于把模糊需求变成能力需求。

示例：

用户输入：

```text
我想做一个公司制度问答机器人。
```

拆解结果：

```text
1. 文档收集
2. 文档解析
3. 数据清洗
4. 权限规则
5. 向量化
6. RAG 问答 Agent
7. 前端聊天界面
8. 企业微信或飞书接入
9. 测试问题集
10. 上线监控
```

输出候选方案：

```text
方案 A：低成本 SaaS 拼装，3 天上线
方案 B：平台认证服务商交付，7 天上线
方案 C：私有化部署，3-4 周上线
```

### 7.4 能力图谱

平台应维护能力之间关系：

```text
OCR → 文档解析 → 文本切分 → Embedding → 向量库 → RAG Agent → 聊天界面
商品图 → 背景去除 → 图像生成 → 文案生成 → 多语言翻译 → 电商发布
合同文档 → 条款抽取 → 风险识别 → 专家复核 → 报告生成
```

能力图谱可用于：

- 自动组合；
- 推荐前置能力；
- 成本估算；
- 风险判断；
- 工作流生成；
- 替代供应商选择。

## 8. 交易与履约系统

### 8.1 三种交易类型

#### 类型 A：即时调用型

适用于 API、模型、工具、Agent。

流程：

```text
搜索 → 查看能力卡片 → 免费试用 → 下单 / 订阅 → API 调用 → 自动结算 → 反馈
```

特点：

- 标准化程度高；
- 可自动执行；
- 适合 Agent 自动采购；
- 可按次 / 按量计费。

#### 类型 B：配置交付型

适用于企业知识库、AI 客服、自动化工作流。

流程：

```text
需求确认 → 资料提交 → 配置开发 → 测试 → 验收 → 上线 → 维护
```

特点：

- 需要商家参与；
- 可设置里程碑；
- 适合担保交易；
- AI 可辅助生成需求说明书。

#### 类型 C：专家项目型

适用于咨询、部署、审计、复杂定制。

流程：

```text
发布需求 → 多商家报价 → 选择服务商 → 签订里程碑 → 交付 → 验收 → 结算
```

特点：

- 非标程度高；
- 客单价高；
- 需要人类审批；
- 早期现金流价值高。

### 8.2 担保交易设计

担保交易流程：

```text
买家付款到平台
↓
平台冻结资金
↓
商家按里程碑交付
↓
买家验收或平台辅助验收
↓
平台分阶段打款
↓
售后期结束
```

适用于：

- 专家服务；
- 项目制方案；
- 私有部署；
- 高风险业务。

### 8.3 里程碑模板

以企业知识库项目为例：

| 里程碑 | 内容 | 付款比例 | 验收方式 |
|---|---|---:|---|
| M1 | 需求确认与方案设计 | 20% | 确认需求文档 |
| M2 | 数据清洗与知识库搭建 | 30% | 样本文档入库成功 |
| M3 | Agent 配置与系统接入 | 30% | 可用测试环境 |
| M4 | 测试验收与上线 | 20% | 100 条测试问题通过约定标准 |

### 8.4 退款与争议处理

需要提前定义：

- 什么情况下可退款；
- API 调用失败如何补偿；
- SLA 不达标如何赔付；
- 项目交付不达标如何仲裁；
- 结果质量争议如何评估；
- 买方提供数据不合格怎么办；
- 需求变更如何追加费用。

建议平台制定商品类型专属规则：

| 商品类型 | 争议重点 | 处理方式 |
|---|---|---|
| API / 模型 | 调用失败、超时、结果异常 | 日志自动判定，按调用退费 |
| Agent | 任务失败、输出不符 | 平台评测 + 用户反馈 |
| 专家服务 | 交付范围、时间、质量 | 里程碑验收 + 仲裁 |
| 方案包 | 效果与预期不符 | 按验收标准判定 |
| 算力 | 宕机、性能不达标 | SLA 赔付 |

## 9. 信任与治理体系

### 9.1 商家认证

认证等级建议：

| 等级 | 名称 | 条件 |
|---|---|---|
| S0 | 未认证 | 仅注册，不能公开销售或仅限测试 |
| S1 | 基础认证 | 实名 / 企业认证，通过基本审核 |
| S2 | 能力认证 | 商品通过平台测试，有可验证案例 |
| S3 | 行业认证 | 在特定行业有交付经验和评价 |
| S4 | 企业级认证 | 安全、合规、SLA、审计能力完善 |
| S5 | 平台精选 | 重点推荐商家，严格筛选 |

### 9.2 能力评级

能力评分由四部分组成：

```text
平台评测分 + 真实调用表现 + 用户评价 + 商家信用
```

示例指标：

| 维度 | 权重 | 指标 |
|---|---:|---|
| 任务效果 | 35% | 准确率、成功率、人工通过率 |
| 运行表现 | 20% | 延迟、可用性、失败率 |
| 成本效率 | 15% | 单任务成本、性价比 |
| 安全合规 | 15% | 数据保留、权限、审计、私有部署 |
| 商业信用 | 15% | 退款率、投诉率、交付准时率、复购率 |

### 9.3 风险等级

| 风险等级 | 场景 | 策略 |
|---|---|---|
| R0 | 格式转换、图片压缩、简单摘要 | 可自动调用 |
| R1 | 文案生成、图片生成、翻译 | 低金额可自动调用 |
| R2 | 客服、销售、内部知识库 | 需要日志和可回滚 |
| R3 | 法律、金融、招聘、医疗辅助 | 需要人工审批 / 专家复核 |
| R4 | 医疗诊断、投资建议、法律结论 | 平台谨慎开放或不开放 |

### 9.4 数据安全策略

必须支持：

- 数据分类；
- 数据脱敏；
- 最小化传输；
- 临时凭证；
- 数据保留声明；
- 数据删除机制；
- 不用于训练声明；
- 私有部署选项；
- 审计日志；
- 供应商安全问卷；
- 企业黑白名单。

### 9.5 日志与审计

每次 Agent 调用都应记录：

```text
谁发起的调用
代表哪个组织
调用了哪个能力
输入摘要是什么
是否包含敏感数据
花了多少钱
结果是什么
是否成功
是否经过人类审批
商家响应时间
错误码
反馈评价
```

日志分级：

- 普通日志：用于计费和监控；
- 审计日志：用于企业合规；
- 风险日志：用于异常行为检测；
- 争议日志：用于仲裁。

### 9.6 Agent 安全

需要防范：

- Prompt injection；
- 工具滥用；
- 越权调用；
- 预算失控；
- 数据外泄；
- 恶意商家诱导；
- 虚假能力卡片；
- 自动下单欺诈。

应对设计：

- 权限最小化；
- 高风险动作审批；
- 调用前策略检查；
- 输出内容安全检查；
- 商家信誉过滤；
- 异常调用限流；
- 可回滚机制；
- 人类确认链路。

## 10. MVP 规划

### 10.1 MVP 定位

MVP 不做大而全，而做：

> **企业知识库 / 文档处理 / AI 客服方向的精选 AI 能力市场，支持人类浏览和 AI Agent API 搜索。**

### 10.2 MVP 目标

90 天内验证：

1. 商家是否愿意上架标准化能力；
2. 买家是否愿意通过平台找 AI 能力；
3. 能否产生真实订单；
4. AI Agent 是否能通过 API 搜索和读取能力卡片；
5. 能否记录调用和反馈数据；
6. 平台是否能从交易中抽佣或收服务费。

### 10.3 MVP 类目

建议只开 3 个一级类目：

```text
1. 企业知识库 / RAG
2. 文档处理 / OCR / 摘要
3. AI 客服 / 售后自动化
```

每个类目准备：

- 5-10 个标准 API / Agent；
- 3-5 个专家服务；
- 2-3 个方案包；
- 1 套测试数据和验收标准。

### 10.4 MVP 功能清单

#### 买家端

- 注册 / 登录；
- 浏览能力分类；
- 搜索能力；
- 查看能力卡片；
- 发布需求；
- 预约咨询；
- 下单；
- 查看订单；
- 验收评价。

#### 商家端

- 入驻申请；
- 商家资料；
- 能力上架；
- 价格配置；
- API 接入说明；
- 订单管理；
- 交付资料上传；
- 收款结算。

#### Agent 端

- Search API；
- Capability Detail API；
- Compare API；
- Trial API；
- Feedback API；
- API Key 管理；
- 权限设置。

#### 平台后台

- 商家审核；
- 商品审核；
- 类目管理；
- 订单管理；
- 评价管理；
- 手动撮合；
- 纠纷处理；
- 数据看板。

### 10.5 MVP 不做的事情

为了避免范围失控，MVP 暂不做：

- 完全自动 Agent 付款；
- 复杂算力调度；
- 全品类开放入驻；
- 广告竞价系统；
- 大规模模型托管；
- 复杂多商家工作流自动编排；
- 国际多币种支付；
- 完全去中心化市场。

### 10.6 MVP 成功指标

90 天指标：

| 指标 | 目标 |
|---|---:|
| 入驻认证商家 | 20+ |
| 上架能力商品 | 50+ |
| 可 API 调用能力 | 15+ |
| 标准方案包 | 5+ |
| 企业线索 | 50+ |
| 真实订单 | 10+ |
| GMV | 10-50 万元 |
| Agent API 调用 | 1000+ |
| 复购客户 | 3+ |
| 平台收入 | 2-10 万元 |

3. 平台撮合服务费；

### 12.2 中期收入

中期收入：

1. API 调用分成；
2. 工作流执行费；
3. 企业订阅；
4. 商家认证；
5. 能力评测；

### 12.3 长期收入

长期收入：

1. Agent 交易网络抽成；
2. 企业 AI 采购系统订阅；
3. 托管与调度费；
4. 能力路由费；
5. 风控与审计服务；
6. 数据洞察服务。

### 12.4 收费示例

| 收入项 | 收费方式 | 示例 |
|---|---|---|
| 专家服务抽佣 | GMV 5%-15% | 2 万项目抽 2000 元 |
| API 调用抽成 | 调用收入 10%-20% | OCR 每次 0.1 元，平台抽 0.02 元 |
| 企业订阅 | 月 / 年费 | 2999-29999 元/月 |

### 12.5 不建议早期过度依赖广告

广告收入可能损害 Agent 推荐可信度。早期应坚持：

> **Agent 推荐排序以匹配度、质量、成本、风险为核心，不应简单卖排名。**

## 16. 风险防控计划

### 16.1 产品风险

**风险**：范围过大，MVP 失焦。  
**措施**：只做 3 个类目，只做必要功能，先跑交易闭环。

### 16.2 市场风险

**风险**：AI Agent 自主采购尚未成熟。  
**措施**：先做人机协同，AI 做搜索、推荐、试用，人类做审批。

### 16.3 供给风险

**风险**：商家质量低。  
**措施**：邀请制、精选、认证、试用、评测、低质淘汰。

### 16.4 需求风险

**风险**：买家不理解能力市场。  
**措施**：用“AI 方案包”和“需求诊断器”降低理解门槛。

### 16.5 合规风险

**风险**：数据泄露、输出误导、责任不清。  
**措施**：风险分级、审批、日志、免责声明、合同模板、数据策略。

### 16.6 技术风险

**风险**：Agent 自动组合效果不稳定。  
**措施**：早期只做推荐组合，不自动执行复杂高风险工作流。

### 16.7 商业风险

**风险**：交易佣金不够覆盖运营成本。  
**措施**：早期结合高客单方案、企业订阅、评测认证收入。

## 19. 关键决策问题

项目启动前需要明确：

1. 第一垂直场景选哪个？
2. 首批商家从哪里来？
3. 交易是先做担保订单，还是先做线索撮合？
4. 是否自己接支付和分账？
5. Agent API 是同步开发，还是第二阶段开发？
6. 能力卡片标准开放到什么程度？
7. 是否允许未认证商家公开上架？
8. 高风险类目是否一开始开放？
9. 平台是否承担结果责任？承担到什么程度？
10. 早期收入目标是 GMV、佣金还是企业服务费？

建议答案：

- 第一场景：企业知识库 / 文档处理 / AI 客服三选一或组合；
- 首批商家：邀请制；
- 交易：先线索 + 担保订单结合；
- 支付：先用第三方支付，后续做分账；
- Agent API：MVP 就做最小版本；
- 能力标准：内部先统一，后续开放；
- 商家：不完全开放；
- 高风险类目：谨慎；
- 责任：按商品类型限定；
- 收入：早期优先真实交易和案例。

## 21. 融资叙事建议

融资时不要讲：

> “我们是 AI 工具淘宝。”

这容易被认为是目录站、撮合平台、低壁垒。

应讲：

> **AI Agent 将成为新的采购与执行主体，但今天的 AI 能力供给是碎片化的。我们建立一个 AI-native 能力交易网络，让模型、Agent、专家、算力和方案都可以被机器理解、调用、交易和评价。**

融资叙事结构：

1. 趋势：AI 从聊天走向行动，Agent 需要外部能力；
2. 问题：能力供给碎片化、不可比较、不可自动采购；
3. 解决：Capability Card + Agent API + 交易结算 + 可信评测；
4. 切入：企业知识库 / 文档处理 / AI 客服；
5. 壁垒：能力标准、真实交易数据、评测体系、商家网络、企业信任；
6. 未来：成为 AI Agent 的能力采购基础设施。
