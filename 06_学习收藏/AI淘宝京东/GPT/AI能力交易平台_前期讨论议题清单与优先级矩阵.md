# AI 能力交易平台：前期讨论议题清单与优先级矩阵

> 版本：v0.1  
> 用途：用于项目早期内部讨论、合伙人沟通、产品立项、MVP 范围确认。  
> 核心背景：我们不是做一个具体 AI 产品，也不是做 AI 工具导航站，而是做一个面向人类与 AI Agent 的 AI 能力交易平台。长期目标是让 AI Agent 可以自动发现、比较、购买、组合并执行外部能力。

---

## 0. 先给结论

前期最需要讨论的不是“网站怎么做”，也不是“要不要做很多类目”，而是下面五件事：

1. **平台边界**：我们到底做平台、交易基础设施，还是做具体交付服务？
2. **第一批客户**：早期到底服务谁？企业老板、AI 服务商、Agent 开发者，还是企业内部 AI 团队？
3. **第一批类目**：从哪个垂直场景切入？不能一开始做所有 AI 能力。
4. **能力卡片标准**：所有商品如何被人类理解，也能被 AI Agent 读取？
5. **交易与信任闭环**：如何让买家敢买、商家敢卖、平台可追责？

我建议前期讨论顺序是：

```text
定位边界
→ 第一批客户
→ 第一批类目
→ 商品标准
→ 交易闭环
→ 信任评测
→ AI Agent 接口
→ 安全权限
→ 商家冷启动
→ MVP 路线图
```

一句话：

> 先把“谁来买、买什么、怎么交付、怎么信任”讲清楚，再谈技术架构和规模化。

---

## 1. 前期讨论的总原则

### 1.1 不要先做“大而全”

这个项目的最终想象空间很大：模型、Agent、技能、专家、算力、行业方案、MCP Server、API、数据处理、评测、安全服务都可以成为能力商品。

但早期如果一开始就做“大而全”，会出现几个问题：

```text
类目太散
商家质量不可控
买家不知道平台到底解决什么
交易链路太复杂
运营成本过高
技术建设失焦
```

前期应该先做一个窄场景，把交易闭环跑通。

---

### 1.2 先做“可信交易”，再做“完全自动化”

长期方向是 AI Agent 自动浏览、自动比较、自动下单、自动组合、自动执行。

但早期不应该假设企业马上允许 AI 自动花钱、自动上传数据、自动调用外部工具。

更现实的阶段是：

```text
AI 自动搜索
AI 自动比较
AI 自动生成推荐方案
AI 自动发起报价/试用
人类确认预算和高风险动作
平台完成担保交易和审计
```

早期口径应该是：

> AI 辅助采购，人类授权决策，平台担保履约。

---

### 1.3 平台不做具体产品，但要做强平台基础设施

“不做产品”不等于“不做能力”。

平台必须做：

```text
商家系统
能力商品系统
搜索匹配系统
交易系统
支付结算系统
交付里程碑系统
评价评级系统
安全权限系统
AI Agent 接口
日志审计系统
争议仲裁规则
```

真正的重点是：

> 不做某一个 AI 客服产品，但要做让别人卖 AI 客服能力的平台。

---

### 1.4 人类页面是表层，机器可读协议是底层

传统平台给人看。

这个平台要同时服务人类和 AI Agent。

因此每一个能力商品都要有两套表达：

```text
人类可读商品页：
- 适合谁
- 解决什么问题
- 价格多少
- 案例如何
- 交付多久
- 售后如何

AI 可读能力卡片：
- input_schema
- output_schema
- pricing
- latency
- SLA
- permissions
- data_policy
- risk_level
- API/MCP endpoint
- composability
- evaluation_metrics
```

这会成为平台未来最重要的差异化。

## 3.1 议题一：平台定位与边界

### 为什么要先讨论

这个项目容易在三个方向之间摇摆：

```text
方向 A：AI 工具导航站
方向 B：AI 服务/项目外包平台
方向 C：AI Agent 能力交易基础设施
```

如果定位不清，产品会同时做目录、撮合、API、专家、算力、模型，最后失去焦点。

### 必须回答的问题

1. 我们到底是不是平台，不做具体 AI 产品？
2. 平台是否可以在早期参与交付撮合？
3. 平台是否允许自营服务？
4. 平台的核心价值是流量，还是信任、交易、能力标准？
5. 面向人类和面向 AI Agent，哪个是短期主入口，哪个是长期主入口？
6. 我们是做国内市场、全球市场，还是先国内验证？
7. 平台最终更像淘宝、天猫、京东、云市场、API 市场，还是采购网关？

### 建议默认答案

我建议这样定：

> 短期形态：精选 AI 能力服务市场。  
> 中期形态：人机协同的 AI 能力采购平台。  
> 长期形态：面向 AI Agent 的能力交易与调用基础设施。

也就是说：

```text
短期靠人类企业买家和服务商交易跑通现金流
中期让 AI 帮助搜索、匹配、报价、推荐
长期让 AI Agent 自动购买、组合和调用能力
```

### 需要形成的产出

```text
1. 一句话定位
2. 对外宣言
3. 不做什么清单
4. 平台与商家的责任边界
5. 短中长期产品形态
```

### 建议写成一句话

> 我们做 AI 能力交易平台，不做具体 AI 产品。平台让模型、Agent、专家、算力和行业方案变成可被人类购买、可被 AI Agent 读取、调用、组合和评价的能力商品。

## 3.2 议题二：第一批目标客户

### 为什么重要

平台要服务两类客户：

```text
人类客户
AI Agent 客户
```

但早期谁真正付钱，必须说清楚。

### 潜在客户类型

| 客户类型 | 需求 | 购买能力 | 早期价值 | 难点 |
|---|---|---|---|---|
| 中小企业老板 | 想用 AI 降本增效，但不懂技术 | 方案包、专家服务 | 客单价可能不错 | 需求模糊，教育成本高 |
| 企业数字化/AI 部门 | 想找外部能力补齐内部项目 | API、模型、专家、部署 | 专业度高，复购潜力强 | 决策周期较长 |
| AI 服务商 | 需要获客和标准化交付 | 店铺、商机、交易工具 | 可作为供给侧 | 需要有买家才愿入驻 |
| Agent 开发者 | 需要可调用外部工具和服务 | API、MCP、能力组件 | 与长期方向一致 | 早期付费能力不一定强 |
| SaaS 公司 | 希望把自身能力 Agent 化 | 能力上架、渠道分发 | 可带来优质供给 | 合作周期长 |
| 企业内部 Agent | 需要受控调用外部能力 | 能力搜索、权限、审计 | 长期最关键客户 | 早期市场还不成熟 |

### 建议第一批客户

我建议第一阶段重点服务：

```text
1. 有明确 AI 项目需求的中小企业 / 成长型企业
2. 做 AI 交付的服务商和专家
3. 正在开发 Agent / 自动化工作流的团队
```

暂时不要直接面向所有普通消费者。

### 需要讨论的问题

1. 第一批买家是企业老板，还是技术团队？
2. 他们最愿意为什么付费？
3. 他们现在通过什么渠道找 AI 服务？
4. 他们最大痛点是“不知道买什么”，还是“不知道谁靠谱”？
5. 他们能接受平台担保交易吗？
6. 他们是否愿意让 AI Agent 参与采购？
7. 他们愿意上传哪些数据？哪些数据绝对不愿上传？
8. 他们的预算区间是多少？

### 需要形成的产出

```text
1. 第一版 ICP 定义
2. 10 个目标客户画像
3. 第一批获客渠道清单
4. 客户访谈问题清单
5. 客户需求优先级
```

## 3.3 议题三：第一批切入类目

### 为什么重要

平台第一阶段不能做所有类目。类目选择错误，会导致：

```text
交易不成立
供给不稳定
交付太复杂
客单价太低
风险太高
买家不愿试
```

### 选择类目的标准

一个适合早期切入的类目，应满足：

```text
1. 企业痛点明确
2. 有付费意愿
3. 交付可以半标准化
4. 不需要极复杂合规
5. 可形成案例
6. 可被 Agent 调用或组合
7. 可沉淀能力卡片
8. 可产生复购或持续调用
```

### 候选类目评估

| 类目 | 需求强度 | 付费意愿 | 标准化程度 | 风险程度 | 早期推荐 |
|---|---:|---:|---:|---:|---|
| 企业知识库 / RAG | 高 | 高 | 中 | 中 | 强推荐 |
| AI 客服 | 高 | 高 | 中 | 中 | 强推荐 |
| 电商内容生成 | 高 | 中高 | 高 | 低中 | 强推荐 |
| 文档处理 / OCR / 摘要 | 高 | 中 | 高 | 低中 | 推荐 |
| 销售线索分析 | 中高 | 中高 | 中 | 中 | 推荐 |
| 合同审查 | 中高 | 高 | 中 | 高 | 谨慎推荐 |
| AI 数据分析 | 中高 | 中 | 中 | 中 | 推荐 |
| 短视频脚本 / 素材 | 中 | 中 | 中高 | 中 | 可选 |
| 模型微调 | 中 | 高 | 低中 | 中 | 适合专家服务 |
| 私有化部署 | 中 | 高 | 低 | 中 | 适合高客单价 |
| 医疗 AI | 高 | 高 | 低 | 极高 | 早期不建议 |
| 金融投资建议 | 高 | 高 | 低 | 极高 | 早期不建议 |
| 招聘自动筛选 | 中 | 中 | 中 | 高 | 谨慎 |
| 算力租赁 | 高 | 中 | 高 | 中 | 不建议第一切口 |

### 建议第一批类目

建议第一阶段选择 3-5 个：

```text
1. 企业知识库 / RAG
2. AI 客服
3. 电商内容生成
4. 文档处理 / OCR / 摘要
5. AI 私有化部署 / 专家服务
```

### 需要形成的产出

```text
1. 第一批类目清单
2. 每个类目的标准商品模板
3. 每个类目的验收标准
4. 每个类目的风险等级
5. 每个类目的示范商家和示范商品
```

## 3.5 议题五：交易闭环与履约机制

### 为什么重要

如果没有交易闭环，平台就是目录站。

AI 能力交易与普通商品不同，交付可能包括：

```text
即时 API 调用
订阅服务
专家咨询
配置交付
私有部署
项目制服务
多能力组合执行
```

因此交易机制必须分层。

### 商品交易类型

| 类型 | 示例 | 交易方式 | 验收方式 |
|---|---|---|---|
| 即时调用型 | OCR API、文案生成 API | 按次扣费 | 调用成功率、结果返回 |
| 订阅型 | AI 客服 Agent 月费 | 月付/年付 | 可用性、SLA |
| 配置型 | 企业知识库问答 | 定金 + 交付尾款 | 测试问题通过率 |
| 专家服务型 | RAG 架构咨询 | 里程碑付款 | 交付文档/系统验收 |
| 方案包型 | AI 客服完整方案 | 项目制 + 运维费 | 上线验收 + 售后 |
| 组合工作流型 | 多 Agent 完成任务 | 任务预算扣费 | 任务整体成功 |

### 建议交易流程

```text
1. 买家/AI Agent 提出需求
2. 平台解析需求
3. 平台推荐能力或商家
4. 买家选择能力
5. 平台生成报价或预估成本
6. 人类确认预算和权限
7. 平台担保收款
8. 商家执行 / 系统调用
9. 平台记录日志
10. 买家验收或系统自动验收
11. 平台分账给商家
12. 形成评价和执行数据
```

### 需要讨论的问题

1. 哪些商品可以自动下单？
2. 哪些商品必须人工确认？
3. 哪些商品需要担保交易？
4. 哪些商品可以立即结算？
5. 专家服务如何分阶段付款？

## 3.8 议题八：安全、权限与预算控制

### 为什么重要

当 AI Agent 可以自动调用能力、上传数据、下单付款时，平台就是一个高风险系统。

### 主要风险

```text
Prompt Injection
恶意能力卡片
恶意 Tool / MCP Server
过度授权
数据泄露
自动扣费失控
Agent 被诱导下单
商家返回恶意内容
供应链攻击
跨 Agent 权限升级
```

### 权限分级

建议将 Agent 权限分成五级：

| 等级 | 权限 | 是否需人工确认 |
|---|---|---|
| L0 | 只能搜索和读取公开能力信息 | 不需要 |
| L1 | 可以试用低风险能力 | 可不需要 |
| L2 | 可以在预算内调用已批准能力 | 视预算而定 |
| L3 | 可以创建订单，但需人类审批 | 需要 |
| L4 | 可以自动下单和续费 | 需要企业授权 |
| L5 | 可以调用高风险能力或上传敏感数据 | 必须严格审批 |

### 预算控制

每个 Agent 应该设置：

```text
单次任务预算
每日预算
每月预算
单能力预算
高风险能力禁止调用
敏感数据上传限制
自动续费限制
```

### 需要讨论的问题

1. 哪些动作必须人工确认？
2. 哪些数据禁止上传？
3. 哪些行业能力禁止自动调用？
4. 商家的 API 是否必须走平台代理？
5. 平台是否保存调用日志？
6. 日志保存多久？
7. 如何处理数据删除请求？
8. 如何防止 Agent 被诱导重复扣费？
9. 如何识别恶意商家？
10. 出现安全事故如何追责？

### 建议默认规则

```text
1. 初期不允许 AI Agent 自主大额付款
2. 所有外部写入动作默认需要人工确认
3. 所有敏感数据上传默认需要授权
4. 所有商家能力先走平台代理调用
5. 所有交易和调用保留审计日志
6. 高风险类目初期只允许人工辅助，不允许全自动
```

### 需要形成的产出

```text
1. Agent 权限等级
2. 预算控制规则
3. 高风险动作清单
4. 数据分级规则
5. 审计日志规则
6. 安全事件应急流程
```

## 5. 早期不建议优先讨论的事项

这些事项重要，但不适合太早深入，否则容易分散注意力。

### 5.1 不要过早讨论复杂融资故事

融资故事可以准备，但现在更重要的是验证：

```text
是否有真实买家
是否有真实商家
是否能产生交易
是否能沉淀能力标准
是否能被 AI 调用
```

### 5.2 不要过早做全球化

先把一个市场、一个语言、一个垂直类目的交易闭环跑通。

### 5.3 不要过早深做算力交易

算力重要，但早期不建议作为核心切口。

原因：

```text
重资产/重运维
价格透明
毛利薄
竞争激烈
对企业买家来说不是最直接问题
```

### 5.4 不要过早开放所有商家自由入驻

早期质量比数量重要。

建议：

```text
邀请制
精选制
认证制
人工审核
平台协助包装商品
```

### 5.5 不要过早追求 AI 全自动付款

AI 自动付款是长期方向，但早期必须有人类审批和预算控制。

## 13. 自检：这份讨论清单还缺什么？

我重新检查后，认为还需要额外补充三件事。

---

### 13.1 补充一：平台是否要做“需求诊断器”

这是非常重要的前台入口。

因为企业客户往往不知道自己要买什么。

他们不会说：

```text
我要 RAG + Embedding + 向量数据库 + LLM Gateway。
```

他们会说：

```text
我想让员工可以问公司制度和产品资料。
```

因此平台应该提供：

```text
AI 需求诊断器
```

流程：

```text
用户输入业务问题
→ AI 拆解任务
→ 平台生成需求说明书
→ 推荐能力商品/商家
→ 发起报价或试用
```

这可能是早期获客和转化的关键。

---

### 13.2 补充二：平台是否要做“能力包装服务”

早期很多商家有能力，但不会商品化。

例如：

```text
一个 AI 工程师会做 RAG，但不会写商品页
一个专家懂行业流程，但不会做 Agent
一个服务商有案例，但不会结构化成能力卡片
```

平台可以提供：

```text
能力包装服务
商品模板
上架辅导
案例整理
能力卡片生成器
```

这能提高供给质量。

---

### 13.3 补充三：平台要尽早沉淀“失败数据”

很多平台只展示成功案例，但 AI 能力平台更需要失败数据。

因为 AI Agent 选择能力时，失败边界非常重要。

每个能力都应该逐渐沉淀：

```text
适合什么场景
不适合什么场景
常见失败原因
需要哪些前置条件
哪些数据质量会影响效果
是否需要人工复核
```

这会让平台更可信。

## 15. 最后一页：项目早期判断框架

每个新想法都用下面这个框架判断是否现在要做：

```text
它是否帮助我们获得第一批买家？
它是否帮助我们获得第一批高质量商家？
它是否帮助我们跑通交易闭环？
它是否帮助能力被 AI Agent 读取和调用？
它是否增强信任、评测、安全或结算？
它是否能在 90 天内验证？
```

如果答案是否定的，就先放后。

早期最重要的不是证明想象空间有多大，而是证明：

> 有人愿意买，有人愿意卖，平台能促成交易，并且这些能力可以逐步被 AI 自动读取、比较、购买和调用。
