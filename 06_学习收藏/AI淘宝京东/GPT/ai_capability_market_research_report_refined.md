> 版本：v1.0  
> 日期：2026-06-06  
> 主题：面向 AI Agent 的能力交易平台 / Agent Commerce Infrastructure  
> 资料来源：基于前期讨论、已生成的机会与风险总结，以及用户上传的 Gemini 相关战略材料进行融合整理。  
> 处理原则：取其精华，去其糟粕；保留 A2A、机器可读、结算、信任、安全、API-first 等核心洞察，剔除过度宏大、过度投机、监管风险高、早期不可执行的内容。

## 0. 执行摘要

本报告研究的不是一个普通的 AI 工具网站，也不是一个单纯的模型市场，而是一个面向未来智能体经济的 **AI 能力交易平台**。

传统电商解决的是：

```text
人如何发现、比较、购买商品
```

这个项目要解决的是：

```text
AI Agent 如何发现、比较、购买、组合、调用和评价外部能力
```

因此，它的本质不是“AI 工具导航站”，也不是“AI 应用商店”，而是一个 **能力交易、调用、结算、评测、安全与治理基础设施**。

一句话定位：

> **AI 时代的淘宝，交易的不是普通商品，而是可被 AI 自动发现、比较、购买、组合和执行的能力。**

更进一步的战略定位：

> **面向 AI Agent 的能力采购、调用与结算网络。**

平台不自研具体 AI 产品，而是让模型提供方、Agent 开发者、自动化工作流开发者、AI 专家、算力供应商、SaaS 服务商、行业解决方案商都可以像开店一样上架能力。买家既包括人类企业，也包括企业内部或第三方 AI Agent。长期看，真正高频的买家会是 AI。

本报告的核心结论如下：

1. **市场趋势成立。** AI 正在从聊天工具转向执行主体，未来大量任务会由 Agent 自动拆解、调用外部工具并完成交易。
2. **市场空白存在。** 现有模型市场、Agent 商店、自由职业平台、算力市场、云市场都只覆盖局部，缺少一个面向 AI Agent 的标准化能力交易层。
3. **真正壁垒不是商品数量，而是能力标准、信任评级、交易数据和安全治理。**
4. **早期不能做大而全。** 最优切入不是纯模型、纯算力，也不是开放式工具目录，而是企业 AI 方案、专家服务和可 API 化 Agent 能力。
5. **AI 是长期主要客户，但早期必须人机协同。** 先让 AI 可搜索、可推荐、可报价，由人类授权下单；再逐步演进到 Agent 自动采购。
6. **Gemini 材料中的 A2A、API-first、机器钱包、SLA 自动仲裁、能力清算网络等观点有价值，但“机器暗网”“高频金融 EA”“Web3 代币经济”等内容要谨慎吸收，不能成为早期主线。**

## 1. 项目定义与市场边界

### 1.1 不是什么

这个项目首先要排除几个误区。

#### 不是 AI 工具导航站

如果平台只是收录工具、分类展示、写介绍、放跳转链接，那么它很容易变成内容站或导航站。导航站的核心问题是：

```text
没有交易闭环
没有履约控制
没有真实执行数据
没有机器可读标准
没有安全治理
没有支付结算
没有复购壁垒
```

AI 工具导航站可以带来短期流量，但很难形成长期护城河。

#### 不是单纯模型市场

模型是重要原材料，但企业真正购买的是结果，而不是模型参数。企业不会因为一个模型参数大就付款，它会为“客服降本”“合同风险识别”“知识库问答上线”“电商内容批量生产”“销售线索自动跟进”付费。

因此，模型市场只是平台的一类供给，不是平台全部。

#### 不是简单专家外包平台

专家服务是重要供给，但传统外包平台的问题是非标、慢、依赖人工沟通，不能满足 AI Agent 高频调用、自动比价、自动组合的需求。

未来专家要被商品化为：

```text
Prompt 模板
行业知识库
审核规则
评测标准
Agent 工作流
半自动服务包
专家兜底服务
行业方案包
```

#### 不是纯算力市场

算力是基础设施，但早期把项目做成纯算力市场并不理想。算力价格透明、竞争激烈、运维重、毛利薄，容易被云厂商和专业 GPU 平台挤压。

算力更适合作为平台后续能力调度的一部分，而不是第一阶段唯一入口。

---

### 1.2 应该是什么

建议定义为：

> **AI 能力交易平台：把模型、Agent、技能、专家、算力和行业方案标准化为可被人类和 AI Agent 发现、比较、购买、调用、组合、评价和治理的能力商品。**

英文表达可以是：

```text
AI Capability Marketplace
Agent Commerce Infrastructure
A2A Capability Routing and Settlement Network
```

中文表达可以是：

```text
AI 能力交易平台
Agent 能力采购平台
AI 能力路由与结算网络
智能体时代的能力交易基础设施
```

其中最准确、最稳妥的名称是：

> **AI 能力交易平台**

它兼具市场属性、交易属性和基础设施属性。

## 2. 宏观趋势分析

### 2.1 从 HCI 到 A2A：买家主体正在变化

过去的互联网主要围绕 HCI，也就是人机交互。

```text
人打开网页
人搜索商品
人比较价格
人点击购买
人使用服务
```

AI Agent 兴起后，未来会出现 A2A，也就是 Agent-to-Agent 或 Agent-to-API 的交互。

```text
Agent 接收目标
Agent 拆解任务
Agent 搜索外部能力
Agent 比较价格、质量和 SLA
Agent 请求授权
Agent 自动调用工具
Agent 组合多个服务
Agent 反馈执行结果
```

这意味着市场中的高频客户可能不再是人类，而是带有预算、权限和目标的 AI Agent。

人类不会消失，但角色会变化：

```text
人类 = 目标设定者 + 预算授权者 + 风险负责人 + 最终验收者
AI Agent = 搜索者 + 比较者 + 调用者 + 执行者 + 反馈者
```

这就是项目最重要的市场判断。

---

### 2.2 AI 能力供给会爆炸，但信任会变得稀缺

未来供给侧会出现大量能力：

```text
模型 API
MCP Server
Agent
Prompt 模板
工作流
自动化脚本
行业知识库
专家规则包
私有化部署服务
RAG 方案
OCR 服务
视频生成服务
算力节点
评测服务
安全审计能力
```

供给爆炸会带来一个反直觉的问题：买家不是缺选择，而是缺信任。

买家真正关心的是：

```text
这个能力是否真实可用？
能不能稳定执行？
是否适合我的行业？
是否支持我的数据格式？
是否会泄露数据？
是否能私有化部署？
出了问题谁负责？
价格是否透明？
效果是否可验证？
能否被我的 Agent 自动调用？
```

因此，平台核心价值不应是“收录最多”，而应是：

> **帮助人类和 AI 找到可信、适配、可调用、可结算、可追责的能力。**

---

### 2.3 从 SaaS 购买到 Agent 能力采购

传统企业软件采购是：

```text
选择 SaaS → 购买账号 → 员工登录使用
```

AI Agent 时代可能变为：

```text
企业设定目标与预算 → Agent 拆解任务 → Agent 采购外部能力 → 平台负责权限、支付、结算、审计和反馈
```

例如企业内部销售 Agent 接到任务：

> 找出最近 30 天内最有可能成交的 200 个客户，并生成跟进话术。

它可能需要调用：

```text
CRM 数据清洗能力
线索评分模型
行业公司信息 API
邮件生成 Agent
电话话术生成 Agent
合规检查能力
人工销售专家审核服务
```

这些能力不一定来自同一家供应商。平台如果能把它们标准化、可组合、可结算，就成为 Agent 的采购入口。

---

### 2.4 模型能力趋同，能力组合和交付成为差异

大模型本身的能力在快速提升，但很多企业落地问题并不只是“模型聪不聪明”，而是：

```text
业务数据怎么接？
权限怎么管？
输出怎么验收？
流程怎么接入？
成本怎么控制？
模型什么时候该换？
专家什么时候介入？
调用失败怎么重试？
结果错误怎么追责？
```

这意味着未来 AI 商业化竞争会从模型层向以下层面转移：

```text
能力组合
工作流编排
场景落地
企业交付
安全治理
成本路由
执行反馈
真实效果评分
```

这正是 AI 能力交易平台可以切入的位置。

## 3. 市场现状与竞争格局

### 3.1 现有市场类型

| 类型 | 代表形态 | 解决的问题 | 局限 |
|---|---|---|---|
| 模型社区 / 模型库 | Hugging Face 等 | 模型发现、开源协作、数据集与 Demo | 偏技术社区，不是完整交易、履约、结算和治理平台 |
| 模型 API 市场 | Replicate 等 | 模型 API 调用与部署 | 偏模型层，难覆盖专家、行业方案、复杂交付 |
| 云厂商 AI 市场 | AWS Bedrock、Azure、Google Cloud 等 | 企业级模型访问、云内治理、集成能力 | 强绑定云生态，不是中立跨平台市场 |
| Agent / GPT 商店 | GPTs、各类 Agent Store | 自定义助手发现与使用 | 多数是面向人类使用，不是完整 Agent 采购与结算网络 |
| 自由职业平台 | Upwork、Fiverr、猪八戒等 | 专家和外包服务交易 | 非标、慢、不适合机器高频调用 |
| 算力平台 | GPU 云、Serverless GPU、去中心化算力 | 训练和推理资源 | 价格竞争强，缺少能力组合与场景交付 |
| 工作流自动化平台 | Zapier、Make、n8n 等 | 应用连接、自动化流程 | 更偏工具连接，不负责能力市场、交易信任和专家服务 |
| 协议与连接层 | MCP、OpenAPI、插件协议等 | AI 与外部工具/数据连接 | 负责连接，不负责商业交易、信用、结算、纠纷和治理 |

结论：现有玩家分别占住了不同层，但都没有完整覆盖：

```text
机器可读能力标准
+ Agent 搜索与采购
+ 交易担保
+ API 调用结算
+ 能力组合编排
+ 实际效果评测
+ 企业权限与安全治理
+ 专家服务兜底
```

这就是平台机会所在。

---

### 3.2 市场空白：Agent 可用的能力交易层

目前市场缺少一个中间层：

```text
供给侧：模型、Agent、专家、算力、SaaS、工具、数据服务
需求侧：企业、人类用户、第三方 Agent、企业内部 Agent
中间层：能力标准化、发现、比较、交易、调用、结算、评测、安全、治理
```

这个中间层就是 AI 能力交易平台。

它不是替代 Hugging Face、AWS、OpenAI、Upwork、RunPod，而是把它们所代表的能力类型纳入一个更高层的交易抽象。

```text
开店系统

```

## 5. 需求端分析

### 5.1 第一阶段需求端：人类企业买家

早期真正能付款的是人类企业客户，尤其是有明确降本增效诉求的中小企业、出海公司、电商团队和内容团队。

典型需求：

```text
AI 客服降本
企业知识库问答
电商商品图文生成
短视频脚本批量生产
合同风险初审
销售线索分析
会议纪要和文档处理
数据报表自动分析
私有化部署和模型微调
```

这些需求有共同特点：

```text
业务痛点明确
企业愿意付费
可以半标准化
可由专家交付
可逐步 API 化
容易沉淀案例
```

---

### 5.2 第二阶段需求端：AI 应用开发者和系统集成商

这类客户已经具备技术能力，但不想重复造轮子。

他们需要：

```text
现成 OCR 能力
文档解析 API
Embedding 服务
RAG 组件
行业问答 Agent
安全审计 Agent
企业微信/飞书/钉钉连接器
模型评测工具
低成本推理 API
部署和运维专家
```

他们关心：

```text
API 是否稳定
文档是否清晰
价格是否透明
SLA 是否可信
能否批量调用
是否支持私有化
是否可嵌入自己的产品
结算是否简单
```

这类需求更适合 AI 原生接口和按量计费。

---

### 5.3 第三阶段需求端：AI Agent

长期看，平台真正高频买家是 AI Agent。

典型场景：

```text
企业采购 Agent 自动找供应商
销售 Agent 自动采购线索分析能力
客服 Agent 自动调用知识库、翻译和工单能力
HR Agent 自动调用简历解析和面试评估能力
财务 Agent 自动调用发票识别和报表分析能力
运营 Agent 自动采购内容生成和分发能力
投研 Agent 自动调用数据源、分析模型和专家审核服务
开发 Agent 自动采购代码审查、安全扫描和部署能力
```

AI Agent 的采购特点：

```text
高频
小额
自动化
强依赖机器可读信息
按成本、延迟、质量、权限和历史表现决策
需要预算约束
需要审计留痕
需要失败回滚和退款机制
```

这要求平台从第一天就具备 AI 可读、API-first 和权限治理设计。

## 6. 核心机会分析

### 6.1 机会一：成为 Agent 采购入口

未来企业内部可能有大量 Agent，但这些 Agent 不可能自己完成所有事情。它们需要外部能力市场。

平台如果能提供：

```text
能力搜索
能力比较
自动报价
权限校验
预算控制
调用执行
结果返回
效果评分
```

就可能成为 Agent 采购外部能力的入口。

这比普通工具商城更底层。

---

### 6.2 机会二：定义机器可读能力标准

普通商品有标题、价格、SKU、库存、物流、评价。

AI 能力商品需要：

```text
输入 Schema
输出 Schema
调用协议
价格模型
延迟
SLA
质量指标
权限需求
数据政策
风险等级
可组合关系
错误码
验收标准
版本信息
```

谁能定义这套标准，谁就有机会成为 AI 能力交易的事实入口。

---

### 6.3 机会三：用真实执行数据建立信任壁垒

传统评价体系依赖文字评论和星级。

AI 能力平台可以建立更强的评分体系：

```text
真实调用成功率
平均延迟
失败率
退款率
复购率
人工介入率
任务完成率
单位成本
行业适配度
安全事件记录
SLA 违约记录
```

这些数据只有交易和调用发生在平台内才能沉淀。

因此平台必须做交易闭环，不能只做跳转。

---

### 6.4 机会四：企业 Agent 需要可信采购网关

企业不会允许 Agent 在开放互联网上随意调用未知工具、上传数据、自动付款。

企业需要：

```text
供应商白名单
预算上限
权限审批
合同与发票
数据边界
日志审计
安全扫描
敏感任务人工确认
失败追责
合规留痕
```

平台可以成为：

> **企业 Agent 的受控采购网关。**

这比普通 C 端 AI 工具市场更有商业价值。

---

### 6.5 机会五：专家能力商品化

专家原本只能按小时卖服务。平台可以帮助专家把经验拆成商品：

```text
行业 Agent
知识库
审核规则
Prompt 模板
评测集
半自动服务包
人工兜底能力
咨询交付套餐
```

这不仅降低专家交付成本，也让 Agent 可以把专家能力纳入工作流。

---

### 6.6 机会六：跨平台中立能力路由

大平台通常服务自己的生态。这个项目可以定位为：

```text
不绑定单一模型
不绑定单一云厂商
不绑定单一 Agent 框架
不绑定单一支付方式
不绑定单一供给类型
```

中立性是机会，也是一种差异化。

## 7. “Gemini 材料”的精华与糟粕

### 7.1 值得吸收的精华

#### 1. A2A 视角

Gemini 材料提出“从人类大卖场到机器流量池”，这个方向是正确的。平台长期不是给人翻网页，而是给 Agent 自动检索和调用。

应吸收为：

```text
平台不是网页货架，而是能力路由与结算网络。
```

#### 2. API-first 原则

平台必须从第一天就设计为 API-first。

应吸收为：

```text
前台给人看，后台给 AI 读。
人类看到商品页，AI 看到能力协议。
```

#### 3. 机器可读能力描述

Gemini 材料强调 JSON、能力标签和标准化 SKU，这非常重要。

应吸收为：

```text
能力卡片 Schema 是平台第一性资产。
```

#### 4. 预充值、预算、结算、SLA 自动仲裁

Agent 高频小额调用必须解决结算效率和争议问题。

应吸收为：

```text
平台需要钱包/预算系统、用量计费、SLA 监控、自动退款、担保交易。
```

#### 5. 沙箱与 API 隔离

Agent 调用外部能力会带来安全风险。

应吸收为：

```text
所有能力商品必须可沙箱测试，平台要做 API 网关、隔离、日志和风控。
```

#### 6. 不做产品，做交易和清算基础设施

这一点与我们此前讨论一致。

应吸收为：

```text
平台做规则、标准、交易、结算、信用、治理，不做具体 AI 产品。
```

---

### 7.2 需要谨慎或剔除的部分

#### 1. “机器暗网”等表述不适合对外使用

它有想象力，但容易造成负面联想。对外应使用：

```text
Agent Commerce Infrastructure
AI Capability Network
可信能力交易网络
```

不建议使用：

```text
机器暗网
黑箱交易网络
```

#### 2. 高频金融交易 EA 不适合作为早期主线

金融自动交易、黄金高频 EA、量化策略售卖等领域监管风险高、纠纷风险高、伦理风险高、合规成本高。它可能带来短期高客单价，但不适合作为平台第一批标杆类目。

建议避开或放入高风险禁止/严格审核类目。

#### 3. Web3 / Tokenomics 不应成为早期核心

代币经济、DePIN、加密激励可以作为未来研究方向，但早期过早引入会带来：

```text
监管复杂
用户理解成本高
支付合规风险
投机属性过强
偏离企业客户需求
```

早期应使用法币支付、企业发票、担保交易、账单结算。

#### 4. 纯算力出海不应成为唯一切口

中国算力出海可能有机会，但涉及跨境合规、数据、网络、支付、制裁、供应稳定性等问题。可作为后续供应链能力，不建议作为唯一定位。

#### 5. 不要过早追求完全自动化

企业不会一开始就允许 AI 自主花钱、自主上传数据、自主调用未知服务。正确路径是：

```text
AI 搜索 → AI 推荐 → 人类授权 → AI 执行 → 平台审计 → 逐步放权
```

## 8. 风险分析

### 8.1 市场时机风险

风险：AI Agent 自动采购尚未完全普及，市场可能存在提前量。

应对：

```text
早期服务人类企业买家
同时把能力商品结构化为 AI 可读
先做 AI 辅助推荐和人类授权下单
逐步演进到 Agent 自动采购
```

---

### 8.2 冷启动风险

风险：没有买家，商家不愿入驻；没有商家，买家不愿使用。

应对：

```text
不做开放大市场
先精选 20 个高质量供给方
找 10 个真实企业需求试单
用人工撮合跑通交易闭环
沉淀案例和评分数据
```

---

### 8.3 巨头竞争风险

风险：OpenAI、AWS、Google、Microsoft、Hugging Face、阿里、腾讯等都有能力做模型市场、Agent 商店、云市场或工具市场。

应对：

```text
避免正面做纯模型市场
避免做单一生态插件商店
强调跨平台中立
聚焦企业交易、交付、结算、评测、安全和专家服务
做巨头生态之间的能力路由层
```

---

### 8.4 信任风险

风险：商家夸大效果，AI 商品真实表现不可控。

应对：

```text
平台认证
试用沙箱
标准测试集
真实执行评分
SLA 记录
退款率和投诉率公开
担保交易
商家保证金
```

---

### 8.5 安全风险

Agent 会读文件、调用 API、写数据库、发邮件、下订单、付款，因此风险远高于普通网页用户。

主要风险：

```text
Prompt Injection
间接 Prompt Injection
恶意能力卡片
恶意 MCP Server
供应链攻击
过度授权
数据泄露
自动扣费失控
Agent 被诱导下错单
跨 Agent 权限升级
日志隐私泄露
```

应对：

```text
零信任架构
最小权限
沙箱执行
工具白名单
高危动作人工审批
预算上限
调用日志
能力签名
商家安全认证
异常调用风控
快速下架与冻结机制
```

---

### 8.6 合规与责任风险

风险：平台涉及企业数据、个人信息、合同、财务、招聘、医疗、法律等敏感场景。

应对：

```text
行业风险分级
早期避开医疗诊断、金融投资建议、自动交易、法律最终意见等高风险领域
对敏感任务要求人工审核
明确责任边界
设定 SLA 与赔付上限
保留审计日志
制定数据处理协议
支持私有化部署
```

---

### 8.7 单位经济风险

风险：纯 API 抽佣、纯算力撮合毛利可能较低。

应对：

```text
早期从高客单价企业方案和专家服务切入
中期做 API 调用抽成和托管
长期做企业安全网关、私有市场和结算基础设施
```

## 9. 最优切入市场建议

### 9.1 不建议第一阶段做什么

不建议从以下方向单点切入：

```text

这些方向要么竞争强，要么合规风险高，要么早期需求不成熟。

> **精选式企业 AI 能力市场：企业方案 + 专家服务 + 可 API 化 Agent 能力。**

```

这些类目的优势：

```text

需要专家交付
容易形成案例
可逐步 API 化
风险可控
```

## 12. 最终市场判断

这个项目的机会不在“做更多 AI 工具”，而在于：

> **当 AI Agent 变成新的工作主体，它们需要一个可信、可调用、可结算、可治理的能力采购市场。**

它最大的想象力不是“AI 淘宝”这个比喻，而是：

```text
人类电商解决人如何买商品
AI 能力平台解决 AI 如何买能力
```

早期应避免大而全，采用：

```text
精选商家
企业场景
人工撮合
担保交易
机器可读能力卡片
AI 辅助搜索和推荐
逐步走向 Agent 自动采购
```

最终愿景：

> **让 AI 像逛淘宝一样，自动发现、比较、购买、组合并执行 AI 能力；让任何专家、模型、Agent、算力和方案商，都能像开店一样出售自己的能力。**

---

## 13. 一句话总结

```text
模型是原材料，算力是能源，专家是工匠，Agent / 技能是产品，
平台负责把它们变成可被 AI 自动发现、购买、组合、执行和评价的能力商品。
```

更短：

> **AI 时代的淘宝，买家主要不是人，而是 AI。**
