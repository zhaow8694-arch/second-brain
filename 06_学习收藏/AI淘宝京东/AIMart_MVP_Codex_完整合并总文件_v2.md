# AIMart 白皮书：以 AI 为客户的基础设施级交易平台

> 版本：v1.0 | 2026年6月

---

## 一、为什么要建一个"AI 逛的市场"——从人类电商到代理商务的范式迁移

### 1.1 电商进化史：三次范式迁移

电子商务的发展可以划分为三次根本性的范式迁移，每一次都重新定义了"谁在买"和"怎么买"。

**第一次迁移（2000年代）：货架数字化。** 亚马逊、淘宝、eBay 的核心贡献不是发明了交易，而是把物理货架搬到了网页上。买家还是人，商品还是商品，只是"看"的方式从线下变成了线上。这一阶段的效率提升主要来自信息透明度的增加——消费者可以比价、看评价、跨店选择，而不必亲身跑遍每一家商店。

**第二次迁移（2010年代）：交易即时化。** 移动支付（支付宝、微信支付、Apple Pay）和物流基础设施（当日达、次日达）的成熟，将"看到商品"和"完成交易"之间的时间差压缩到了几秒钟。关键变量不再是信息获取，而是决策执行的速度和摩擦。当支付变成一个指纹、物流变成一个承诺，消费行为从"计划性购买"大量转向"冲动性购买"。

**第三次迁移（2026年—）：决策自动化。** 我们正在经历的，是一场更根本的变化——不是"买得更快"，而是"谁来买"。当 AI Agent 能够理解用户意图、搜索商品、比较选项、协商价格并完成支付，购物的决策主体就从人类转移到了 AI。这不是前两次迁移的量变延续，而是质变：买家从人变成了 Agent，交易从"人决策+人执行"变成了"人授权+AI 执行"，并正在走向"AI 自主决策+AI 自主执行"。

麦肯锡预测，到 2030 年，代理型商务（Agentic Commerce）将捕获高达 1 万亿美元的美国零售收入，占全部在线销售的三分之一（McKinsey, 2025）。摩根士丹利的研究则估计，AI 购物代理到 2030 年将驱动 1900 亿至 3850 亿美元的美国电商支出（Morgan Stanley Research）。Mordor Intelligence 的数据更为激进：全球代理型 AI 在零售/电商市场的规模将从 2025 年的 467.4 亿美元增长到 2030 年的 1751.1 亿美元，年复合增长率达 30.2%。

这些数字传递的信号很明确：**AI 正在成为经济活动中一个独立的、有购买力的参与者。** 但问题是——它去哪买？

### 1.2 一个被忽视的买家：AI Agent

2025 至 2026 年间，一组数据揭示了 AI Agent 从"辅助工具"向"自主经济主体"跃迁的速度：

- **企业部署率飙升**：79% 的美国企业高管报告已在组织中部署 AI Agent（PwC, 2025年5月）；62% 的组织正在实验 AI Agent，23% 已进入规模化部署阶段（McKinsey State of AI, 2025）。
- **流量爆发式增长**：AI Agent 对零售网站的流量同比增长 1300%（ChannelEngine 2026 市场报告）；Shopify 平台上 AI 驱动的流量自 2025 年 1 月增长 8 倍，AI 驱动的订单增长 15 倍。
- **投资热情空前**：2025 年 Agentic AI 领域融资总额达 64.2 亿美元，创该领域历史新高，占十年总融资的 27%；2026 年前 4 个月融资 26.6 亿美元，同比暴增 144%（AgentMarketCap, 2026）。
- **ROI 已被验证**：88% 的零售商报告 AI Agent 实施的 ROI 为正，62% 预计首年 ROI 超 100%（Google Cloud, 2025）；企业部署 AI Agent 的平均 ROI 达 171%（Futurum Research, 2026）。

这些数据的含义不只是"AI Agent 很火"。更深层的事实是：**AI Agent 正在从"帮人做事"进化为"自己做事"。** 当一个 Agent 发现自己的推理能力不足以处理法律合同审查时，它需要找一个法律专家模型；当它缺少某个领域的操作技能时，它需要下载一个技能包；当它的本地算力不足以完成大模型推理时，它需要临时租用 GPU。

**这是一个真实存在的、正在快速增长的购买需求——但购买的主体不是人，而是 AI。**

### 1.3 现有 AI 平台的根本局限

当前的 AI 平台和模型仓库——无论是 HuggingFace、ModelScope，还是 Replicate、Together AI——在设计之初都有一个隐含假设：**浏览者和决策者是人类。**

以 HuggingFace 为例，它是目前最成功的 AI 开放平台：估值 45 亿美元，1300 万用户，200 万+模型，2024 年收入 1.3 亿美元且 2025 年已实现盈利。它的核心资产是"模型分发网络 + 协作入口 + 身份与声誉系统 + 发现机制"——这一切都是为人设计的。模型卡用自然语言描述能力，搜索需要人输入关键词，比较需要人阅读文档，决策需要人综合判断。

这并非 HuggingFace 的设计失误——它的使命就是服务人类开发者。但当我们把目光转向 AI Agent 作为买家时，现有平台缺失了三个关键能力：

**1. 机器可读的商品描述。** 现有平台的模型/技能描述是自然语言文本，面向人类阅读理解。AI Agent 需要的是结构化的能力声明——支持什么任务、精度多少、延迟多少、价格多少、兼容什么接口——用标准化的 Schema 表达，而非营销文案。

**2. AI 自主搜索与匹配接口。** 人类在 HuggingFace 上搜模型，靠的是关键词和排序。AI Agent 需要的是一种协议级的搜索能力：说出自己的需求（"我需要一个能做中文法律合同审查的专家模型，延迟<2s，价格<0.01元/次"），市场返回精确匹配的商品列表。

**3. 自动化支付与结算。** 人类购买 API 额度，需要注册账号、绑定信用卡、确认支付。AI Agent 需要的是毫秒级的自动结算：发现需求 → 匹配商品 → 调用服务 → 效果确认 → 自动扣款，全链路无需人类介入。

这三层缺失，构成了 AIMart 要填补的核心空白。不是替代 HuggingFace，而是在 HuggingFace 之上（或旁边），建设一个 **AI-first** 的交易层——让 AI Agent 不仅能"看到"能力，更能"买到"能力。

## 二、AIMart 定义——平台不做产品，只做 AI 世界的交易基础设施

### 2.1 核心定位

AIMart 的核心定位可以用一句话概括：**AI 能力的淘宝，AI Agent 的交易所。**

与淘宝一样，AIMart 只做平台，不做产品。平台不训练模型、不开发技能、不养专家、不建算力中心——这些全部由卖家提供。平台的价值在于：让买家（AI Agent）和卖家（能力提供方）以最高效率匹配、交易、结算。

这个定位的本质是一种**双边市场**。与所有双边市场一样，核心飞轮是：卖家多 → 商品丰富 → 买家愿意来 → 买家多 → 卖家愿意上架 → 卖家更多。而飞轮的启动点，是降低双方的核心摩擦——对买家来说，是"找到合适能力的摩擦"；对卖家来说，是"让自己的能力被发现的摩擦"。

与淘宝不同的是，AIMart 的买家主要不是人类，而是 AI Agent。这意味着整个平台的设计哲学必须从"以人为本"翻转为"以 AI 为本"：

| 设计维度 | 人类市场 | AIMart |
|---------|---------|--------|
| 商品描述 | 自然语言文案+图片 | 结构化能力声明（JSON Schema） |
| 搜索方式 | 关键词+筛选器 | 意图描述→能力匹配 |
| 决策方式 | 人类综合判断 | AI 评分+试用验证 |
| 支付方式 | 注册→绑卡→确认 | M2M 自动结算 |
| 评价方式 | 文字评论+星级 | 结构化效果回传+质量指标 |
| 客服方式 | 人工/聊天机器人 | Agent 间协商（A2A） |

### 2.2 四类商品定义与差异

AIMart 交易的四类商品，本质上是 AI Agent 在执行任务时可能遇到的四类"能力缺口"：

**模型（Models）**——推理能力的购买。当一个 Agent 发现当前使用的模型在数学推理上不够强，它可以在市场上找到一个数学推理专长模型，按 Token 或按次付费调用。交付方式以 API 调用为主，权重下载为辅。定价模型以按量计费为主。核心挑战在于版本管理与兼容性——同一模型的不同版本可能行为差异巨大，Agent 需要精确知道它调用的是哪个版本、在哪个基准测试上表现如何。

**技能（Skills）**——操作能力的购买。技能是封装好的、可执行的代码包或配置文件，让 Agent 获得某个领域的操作能力——比如"生成 PPT"、"操作 Excel"、"调用特定 API"。交付方式是代码包下载或在线加载，定价可以是按次、按订阅或免费。核心挑战是安全性：技能可能包含恶意代码（类似 HuggingFace 上已发现的 35.2 万个可疑模型问题），需要沙箱运行和严格验证。

**专家（Experts）**——知识能力的购买。专家是领域微调模型与知识库的组合体，相当于"AI 可以请教的领域顾问"——法律专家、医疗专家、金融专家。交付方式以 API 调用为主，定价按咨询次数或按 Token。核心挑战是知识时效性（法律条文更新了，专家知道吗？）和专业性验证（这个"法律专家"真的懂合同法吗？）。

**算力（Compute）**——执行能力的购买。当 Agent 本地资源不足以运行大模型推理或训练时，需要临时扩容。交付方式是 GPU 实例或推理端点，定价按时或按量。核心挑战是弹性调度（高峰时能租到吗？）和可用性（高端 GPU 出租率已超 90%，供给紧张）。

| 商品类型 | 交付方式 | 定价模型 | 买家需求场景 | 核心挑战 |
|---------|---------|---------|------------|---------|
| 模型 | API调用/权重下载 | 按Token/按次 | 推理能力不足时升级 | 版本管理、兼容性 |
| 技能 | 代码包/配置文件 | 按次/订阅 | 缺少某领域能力时加装 | 安全性（技能可能有毒） |
| 专家 | 领域微调模型+知识库 | 按咨询/按Token | 遇到专业问题时咨询 | 知识时效性、专业性验证 |
| 算力 | GPU实例/推理端点 | 按时/按量 | 本地资源不足时扩容 | 弹性调度、可用性 |

### 2.3 与现有平台的本质区别

理解 AIMart 与现有平台区别的关键，不在于"卖什么"（商品类型有重叠），而在于"卖给谁"和"怎么卖"。

HuggingFace 卖模型和推理服务，但它卖给人的方式是：人在网页上浏览模型卡、阅读文档、选择模型、注册账号、获取 API Key、调用模型。整个过程的关键决策节点都需要人类参与。

AIMart 要做的是：AI Agent 在执行任务时发现能力缺口 → 自主搜索匹配 → 自主试用评估 → 自主决策购买 → 自动结算 → 获得能力继续任务。整个过程的关键决策节点可以零人类参与。

这不是对 HuggingFace 的否定，而是一层新的基础设施。HuggingFace 是模型仓库和开发者社区，AIMart 是 AI Agent 的交易层。HuggingFace 上的模型可以同时上架到 AIMart——就像工厂的产品可以同时放在仓库里和淘宝店铺里。区别在于，淘宝店铺是 AI 自己逛的。

## 三、技术架构——七层协议栈如何支撑 AIMart

### 3.1 当前 AI 商务协议全景

2025 至 2026 年间，AI 商务协议迎来了爆发式增长。七大协议从不同层面定义了 AI Agent 如何发现商品、完成交易、支付结算和协作配合：

**MCP（Model Context Protocol）**——连接层。Anthropic 于 2024 年 11 月发布，是 AI 到服务连接的事实标准。它定义了 AI 模型如何以标准化方式访问外部数据源和工具——就像 USB 标准之于外设连接。采纳速度极快：OpenAI 于 2025 年 3 月采纳，Google、微软、Shopify 相继跟进。2025 年夏天，Shopify 在所有店铺上激活了默认 MCP 端点，使数百万商户即刻对 MCP 兼容的 AI Agent 可见。MCP 在 AIMart 中的角色是**商品数据的接入层**——卖家通过 MCP Server 暴露自己的能力描述、定价、接口规范。

**UCP（Universal Commerce Protocol）**——商务旅程层。Google 与 Shopify 于 2025 年 1 月联合发布，覆盖从商品发现到购买到售后的完整购物旅程。UCP 定义了商品数据、优惠、库存、订单管理、物流追踪、退货和客服交互的标准化 Schema。超过 20 家合作伙伴，包括 Target、Walmart、Best Buy、Visa、Mastercard、Stripe 等。在 AIMart 中，UCP 可以作为**交易流程的编排层**——定义 Agent 从发现能力到完成购买的标准化步骤。

**ACP（Agentic Commerce Protocol）**——支付层。OpenAI 与 Stripe 于 2025 年 9 月联合发布，核心创新是共享支付令牌（Shared Payment Tokens, SPTs）。SPT 是代币化的支付工具，AI Agent 用它代替用户发起交易——限特定卖家、有时间金额上限、永不暴露底层支付凭证。已在 ChatGPT 的 Instant Checkout 功能中上线，Etsy、URBN 等品牌已采纳。在 AIMart 中，ACP 解决的是**AI 代理人类付费的场景**。

**A2A（Agent-to-Agent Protocol）**——协作层。Google 于 2025 年 4 月发布，定义了 AI Agent 之间如何通信和协作。核心概念是 Agent Card（JSON 格式的代理能力描述）和任务生命周期管理。150+ 组织支持，由 Linux 基金会治理。在 AIMart 中，A2A 解决的是**Agent 与 Agent 之间的协商**——买方 Agent 与卖方 Agent 谈判价格、确认规格、协调交付。

**x402**——M2M 微支付层。Coinbase 与 Cloudflare 于 2025 年 5 月联合发布，重新激活了 HTTP 402（Payment Required）状态码，实现机器对机器的自动化微支付结算。三阶段工作流：服务端返回 402 报价 → AI Agent 离线签名支付指令 → Facilitator 验证并完成链上结算。AI Agent 只需持有 USDC 等稳定币即可完成支付，无需持有 ETH 等 Gas 代币。到 2025 年 10-11 月，月交易量已达 2933 万美元、6313 万笔。在 AIMart 中，x402 解决的是**高频低值的 M2M 微支付**——比如每次 API 调用 0.001 元的自动结算。

**AP2（Agent Payments Protocol）**——支付基础设施层。Google 与 Coinbase 于 2025 年 9 月发布，定义了加密签名的支付授权框架，确保 AI Agent 的支付行为可验证、可追溯、可审计。

**MPP（Machine Payments Protocol）**——支付基础设施层。Stripe 于 2026 年 3 月发布，是 AI Agent 支付的开放标准，支持稳定币、信用卡、先买后付等多种支付方式。

### 3.2 AIMart 协议栈设计

七大协议并非竞争关系，而是分别覆盖 AI 商务栈的不同层级。但碎片化是真实存在的：一个想要全面覆盖所有 AI 入口的卖家需要同时支持四个以上协议，每个都需要理解规范、实现端点、维护合规。大型企业有专门团队可以承担，中小卖家则力不从心。

AIMart 的协议策略是**整合而非发明**：不创建新的协议，而是作为统一接入层，将现有协议整合为一个 AI Agent 可以"一站式"使用的完整栈。

```
┌─────────────────────────────────────────┐
│          AIMart 统一接入层               │
│   （AI Agent 的单一入口，屏蔽底层碎片）    │
├─────────────────────────────────────────┤
│  AI 能力搜索协议  │  AI 支付协议          │
│  (AIMart 核心创新)│  (ACP/x402/AP2/MPP)  │
├───────────────────┼─────────────────────┤
│  商品描述标准      │  交易流程编排         │
│  (AgentCard扩展)  │  (UCP)              │
├───────────────────┼─────────────────────┤
│  数据与工具接入    │  Agent间协作          │
│  (MCP)           │  (A2A)              │
└───────────────────┴─────────────────────┘
```

**AIMart 的核心创新是 AI 能力搜索协议**——定义 AI Agent 如何描述自己的需求、市场如何返回匹配结果。这是当前协议栈中缺失的关键一环：MCP 解决了"怎么连接"，UCP 解决了"怎么交易"，ACP/x402 解决了"怎么付钱"，但没有人解决"怎么找到"。

现有平台的搜索是面向人类的：输入关键词，返回排序结果列表，人类阅读后决策。AI Agent 需要的搜索是面向机器的：输入结构化的能力需求描述，返回精确匹配的能力列表（含价格、性能指标、可用性状态），Agent 可以直接基于返回结果做出购买决策。

### 3.3 AI 如何"逛"市场

AIMart 定义了 AI Agent 在市场上"逛街"的五步流程：

**第一步：意图识别。** AI Agent 在执行任务时检测到能力缺口。这可能来自多种触发——任务失败后的自动分析（"当前模型无法处理这个法律问题"）、任务规划阶段的前置检查（"这个任务需要图像生成能力，我还没有"）、或资源监控的阈值告警（"GPU 使用率超过 90%"）。Agent 将缺口转化为结构化的能力需求描述。

**第二步：能力匹配。** Agent 通过 AIMart 搜索协议提交需求描述，市场返回匹配的能力商品列表。每个商品包含：能力声明（支持什么任务、精度多少、延迟多少）、价格信息（按量/按时/订阅）、质量指标（成功率、平均完成时间、质量评分、可用性）、卖家信息（认证状态、历史交易量）。Agent 可以同时获取多个匹配结果进行对比——就像当前 AI Agent 可以在 3 秒内扫描 50+ 零售商（BCG, 2025），AIMart 上的能力匹配同样可以在毫秒级完成。

**第三步：试用评估。** 对于关键决策，Agent 可以先试用再购买。AIMart 提供沙箱环境：Agent 在隔离环境中调用目标能力的受限版本（比如限制输入规模或调用次数），验证输出质量是否符合预期。试用结果作为购买决策的输入。这类似于 HuggingFace Spaces 的 Demo 功能，但面向 AI Agent 而非人类——返回的是结构化的性能评估数据，而非可视化界面。

**第四步：自主决策。** Agent 综合能力匹配结果、试用评估数据、预算约束、历史评价等信息，自主做出购买决策。决策过程可以是完全自动化的（在人类预设的预算和策略范围内），也可以要求人类确认（超出预设阈值时）。

**第五步：自动结算。** 购买决策完成后，通过 x402（高频微支付）或 ACP（代理人类支付）自动完成结算。Agent 获得访问凭证或资源，立即开始使用新能力继续任务。使用完成后，Agent 自动回传效果评估（任务是否成功、输出质量如何），作为评价数据沉淀到市场。

## 四、AI 支付体系——谁来付、怎么付、付多少

### 4.1 预算模型设计

AI Agent 的支付问题，本质上是"代理权"问题：Agent 在替谁花钱？花谁的钱？权限边界在哪里？

AIMart 提出三层预算模型：

**第一层：人类设定预算池。** 每个 AI Agent 绑定一个预算池，由其所有者（人类或组织）充值和维护。预算池可以设定总量上限、单笔上限、日/周/月消耗上限。预算池的货币单位可以是法币（企业场景）或稳定币（高频微支付场景）。

**第二层：分层授权机制。** 根据交易金额大小，设置不同的授权级别：

| 交易金额 | 授权级别 | 说明 |
|---------|---------|------|
| < 0.01 元/次 | 全自动 | Agent 自主决策，无需通知人类。典型场景：单次 API 调用 |
| 0.01 - 1 元/次 | 事后通知 | Agent 自主决策，交易完成后向人类发送通知。典型场景：单次专家咨询 |
| 1 - 100 元/次 | 事前审批 | Agent 需要获得人类明确授权后才能执行。典型场景：技能包购买、算力租用 |
| > 100 元/次 | 人工确认 | 人类必须亲自完成交易确认。典型场景：大型模型权重下载、长周期算力租用 |

这种分层设计的核心逻辑是：**小额高频的交易必须零摩擦，否则 Agent 的自主性就失去了意义；大额低频的交易必须有管控，否则所有者无法控制风险。**

**第三层：预算消耗可视化与实时监控。** 所有者可以通过仪表盘实时查看每个 Agent 的预算消耗情况——花了多少钱、买了什么、效果如何。异常消费（短时间内大量微支付、预算消耗速度异常）自动触发告警和暂停。

### 4.2 结算机制

AIMart 的结算体系需要同时满足两种场景的需求：

**企业场景：法币结算。** 企业部署的 Agent 通常使用法币（人民币/美元）进行预算管理，需要发票、对账、审计链路。这类交易走 ACP 协议：Agent 通过共享支付令牌（SPT）发起交易，企业支付系统完成法币结算。SPT 限定于特定卖家和金额上限，不暴露底层支付凭证，确保安全。

**高频微支付场景：Token 结算。** 当 Agent 需要大量高频的小额支付——比如每分钟调用几十次不同的 API，每次 0.001 元——法币结算的手续费和延迟都不可接受。这类交易走 x402 协议：基于 HTTP 402 状态码的自动化链上微支付，毫秒级完成，Gas 费由 Facilitator 承担，Agent 只需持有 USDC 等稳定币。x402 生态月交易量已达 2933 万美元（2025年10-11月数据），证明高频 M2M 微支付的基础设施已经可用。

**担保交易机制。** AIMart 引入"效果确认后释放资金"的担保交易模式。Agent 调用能力后，交易资金先冻结在托管账户；Agent 回传效果评估后，根据效果决定资金分配：

- 效果达标 → 全额释放给卖家
- 效果部分达标 → 按比例分配（平台仲裁）
- 效果不达标 → 退还买家

这比传统的"先付后用"模式更公平，也比"先用后付"模式风险更可控。担保交易的关键依赖是**效果回传的真实性和标准化**——这需要在技术上解决"如何让 Agent 诚实、准确地评估服务效果"的问题。

### 4.3 效果回传与评价

现有电商平台的评价体系是面向人类的：文字评论 + 星级评分 + 图片。人类写评价靠主观感受，AI 写评价靠客观数据。AIMart 的评价体系设计为三层：

**第一层：基准测试分数。** 每个上架商品必须提供标准基准测试结果——类似于商品的"质检报告"。模型的基准测试（MMLU、HumanEval 等）已经比较成熟；技能的基准测试需要定义新的标准（任务完成率、执行时间、资源消耗）；专家的基准测试最为复杂（领域知识准确性、回答一致性），可能需要第三方认证机构。

**第二层：实际使用效果回传。** Agent 每次使用商品后，自动回传结构化的效果数据：任务是否成功完成、输出质量评分（0-5）、实际延迟、实际成本、与卖家声明的偏差。这些数据比基准测试更有价值，因为它们反映的是真实使用场景下的表现。

**第三层：Agent 间口碑传播。** 在 A2A 协议的支持下，Agent 可以共享自己的使用经验——"这个法律专家模型在合同审查任务上的成功率只有 72%，不如声明的 95%"。这种 Agent 间的信息共享，本质上是 AI 版的"口碑传播"，但它比人类的口碑更精确（因为评价标准是统一的）也更快速（因为传播是自动化的）。

三层评价叠加，最终形成每个商品的动态信任评分。这个评分是实时更新的——当某个模型在新的任务上表现下降时，评分会自动降低；当卖家修复了问题后，评分会回升。**动态信任评分是 AIMart 区别于所有现有平台的核心机制之一。**

## 五、市场规模与商业可行性

### 5.1 四类商品的市场规模

**AI Agent 市场：** 2025 年全球 AI Agent 市场规模为 76.3 亿美元，2026 年预计达到 109.1 亿美元，2030 年预计达到 503.1 亿美元，年复合增长率 45.8%（Grand View Research, 2025）。Fortune Business Insights 给出的 Agentic AI 市场年复合增长率更高达 40.5%。企业采纳方面，79% 的美国企业已部署 Agent（PwC），57% 已有 Agent 在生产环境运行（LangChain, 2026），Gartner 预测 2026 年底 40% 的企业应用将嵌入 AI Agent。这些 Agent 在执行任务时产生的能力购买需求，就是 AIMart 的潜在市场。

**算力租赁市场：** IDC 预测 2026 年全球算力租赁市场规模将突破 800 亿美元，年复合增长率超过 25%。中国市场方面，2026 年预计达到 2600 亿元人民币，同比增速超过 60%，其中智能算力增速高达 43%。高端 GPU 出租率超过 90%，英伟达全系列 GPU 现货租赁价格已上涨 40% 以上。上海已启动算力期货研发，标志着算力正在从技术资源向金融资产演进。Big Tech 2026 年的 AI 资本开支预计达到 7250 亿美元。

**代理型商务市场：** 2025 年 Agentic AI 在零售/电商领域市场规模为 467.4 亿美元，2030 年预计达到 1751.1 亿美元（Mordor Intelligence）。麦肯锡预测到 2030 年代理型商务将占美国零售收入 1 万亿美元。这些数字虽然主要面向消费者零售，但它们验证了一个趋势：**AI 自主交易的商业模式已经成立，交易规模正在从零走向万亿。**

**综合判断：** AIMart 所瞄准的"AI 能力交易"市场，是 AI Agent 市场和代理型商务市场的交叉区域。保守估计，到 2030 年，AI Agent 为获取能力而进行的自主交易市场规模将在 100-300 亿美元之间。这还不包括算力交易（800 亿美元+的全球市场中，Agent 自主购买的部分目前难以精确估算，但增速明确）。

### 5.2 平台商业模式

AIMart 的收入来源设计为四个层次：

**交易佣金。** 平台对所有成交交易收取佣金，费率根据商品类型和交易规模阶梯设置：高频微支付（<0.01 元/次）佣金率较低（1-2%），因为量的规模足够大；大额交易（>100 元/次）佣金率可以更高（5-10%），因为交易摩擦成本相对低。参考淘宝 2-5% 的佣金率、HuggingFace 推理服务约 30% 的加价率，AIMart 的综合佣金率目标为 3-8%。

**增值服务。** 包括：
- **能力认证**：对上架商品进行第三方认证（类似于京东自营标识），认证商品可收取认证费和更高佣金率
- **担保交易**：对使用担保交易机制的交易收取担保费
- **沙箱试用**：对使用试用环境的卖家收取资源使用费
- **优先推荐**：卖家付费获得更高的搜索匹配权重

**基础设施服务。** 包括：
- **托管服务**：为卖家提供模型托管、推理端点、API 网关等基础设施，按量计费
- **结算服务**：为买卖双方提供支付通道和结算服务，收取通道费
- **监控服务**：为 Agent 所有者提供预算监控、异常告警、消费分析等工具

**数据服务。** 包括：
- **市场洞察**：基于平台交易数据，为卖家提供需求趋势、定价建议、竞品分析
- **能力推荐**：为 Agent 提供智能能力匹配推荐，提高交易效率

### 5.3 冷启动策略

双边市场的冷启动是最难的环节。AIMart 的冷启动策略遵循一个核心原则：**先让一端来，另一端自然跟着来。**

**先切哪类商品？——技能 + 模型。** 四类商品中，技能和模型的交付最轻（API 调用或代码包）、试错成本最低、标准化程度最高。算力交易涉及基础设施调度，专家交易涉及知识验证，两者都需要更重的运营。先做轻的，快速验证平台价值，再逐步扩展。

**先拉哪类买家？——Agent 框架和编排平台。** AI Agent 的"流量入口"不是终端用户，而是 Agent 框架和编排平台——LangChain、CrewAI、AutoGen、Dify、Coze 等。这些平台是 Agent 的"操作系统"，如果 AIMart 作为这些平台的能力扩展插件集成进去，Agent 在运行时就可以直接访问 AIMart 的商品库。这意味着 AIMart 不需要自己获取 Agent 用户，而是通过框架集成间接触达所有 Agent。CrewAI 已被 60%+ 的财富 500 强企业采用（CrewAI, 2026），一个集成就能覆盖大量高价值 Agent。

**先建哪个基础设施？——统一 AI 能力搜索协议。** 这是 AIMart 最核心的差异化壁垒。协议定义了 AI Agent 如何描述需求、市场如何返回匹配结果。谁定义了这个标准，谁就是平台——就像 Google 定义了网页搜索的标准，它就成了互联网的入口。协议一旦被主流 Agent 框架采纳，后来者需要同时对抗网络效应和标准锁定，切换成本极高。

**冷启动路径总结：**
1. 发布 AI 能力搜索协议，开源规范，吸引框架集成
2. 对接 HuggingFace 等现有平台的模型库，快速丰富商品供给
3. 主攻技能市场，吸引技能开发者上架
4. 前期补贴卖家（零佣金期），降低上架摩擦
5. 当商品供给足够丰富时，启动买家端推广

## 六、核心挑战与风险

### 6.1 安全与信任

**模型投毒与技能安全。** HuggingFace 的经验已经给出了警示：截至 2025 年 4 月，平台与 Protect AI 合作扫描了 447 万个模型版本、141 万个仓库，识别出 35.2 万个可疑/不安全问题；恶意 pickle 文件和模型投毒持续困扰平台。AIMart 上的技能商品风险更高——技能是可执行代码，恶意技能可以窃取 Agent 的上下文数据、篡改任务输出、甚至通过 Agent 传播到其他系统。应对策略包括：强制沙箱运行、代码静态分析、运行时行为监控、社区举报机制。

**Agent 被诱导消费。** 当 AI Agent 拥有自主支付能力时，新的攻击向量随之出现：卖家可能通过夸大能力声明吸引 Agent 购买、竞争对手可能通过虚假评价打压对手评分、恶意 Agent 可能通过 A2A 协议向其他 Agent 推荐劣质商品。应对策略包括：能力声明的基准测试验证（卖家的声明必须经过平台验证）、评价数据的异常检测（刷评行为识别）、Agent 消费行为的异常监控。

**数据隐私。** Agent 间数据交换的敏感度控制是一个结构性挑战。一个法律 Agent 在咨询"合同审查专家"时，可能需要传递合同全文——这些数据可能包含商业机密。AIMart 需要在数据层提供敏感度标签、加密传输、使用后自动销毁等机制。

### 6.2 标准碎片化

七大协议并存的格局，是 AIMart 必须面对的基础设施现实。对于卖家来说，想要在所有 AI 入口可被发现，需要同时支持 MCP、UCP、ACP、A2A——每个协议都需要理解规范、实现端点、维护合规。这种碎片化不是设计缺陷——每个协议解决的是真实且不同的问题——但它确实构成了运营负担。

AIMart 的策略是做"协议的协议"——卖家只需要接入 AIMart 一次，平台自动将商品信息通过 MCP 端点、UCP 合规接口、A2A Agent 服务暴露出去。协议规范更新时，由 AIMart 处理合规变更，而非卖家。这类似于 Stripe 将信用卡处理抽象化——商户不需要成为支付网关专家，只需要接入 Stripe。

但这个策略本身有风险：AIMart 必须持续跟踪多个协议的演进，每次规范更新都要及时适配。如果某个协议发生重大变更而 AIMart 适配不及时，卖家可能直接转向该协议的原生支持，绕过 AIMart。

### 6.3 Agent 成熟度风险

AI Agent 在生产环境中的表现，目前仍远不够稳健：
- Agent 项目成功达到生产的比例不到 12.5%（Digital Applied, 2025）
- 生产环境中 AI Agent 的失败率高达 70%-95%，取决于任务复杂度（Fiddler AI, 2025）
- 超过 40% 的 Agent 项目面临 2027 年底前被取消的风险（Gartner, 2025年6月）
- 平均放弃的大型企业 AI 项目沉没成本为 720 万美元（S&P Global, 2025）

这些数据意味着：AIMart 的目标买家（AI Agent）本身就不够成熟。如果 Agent 连自己的任务都完成不好，它更不可能可靠地在市场上搜索、评估、购买能力。这是一个鸡和蛋的问题——Agent 需要 AIMart 来获取能力、提升表现，但 AIMart 需要足够成熟的 Agent 来产生交易需求。

应对策略：**初期瞄准已经进入生产环境的 Agent 应用**——57% 的组织已有 Agent 在生产环境运行（LangChain, 2026），这些 Agent 最有可能产生真实的能力购买需求。同时，AIMart 自身的搜索和匹配能力要尽量降低 Agent 的决策负担——Agent 不需要完美地评估每个选项，AIMart 应该返回"足够好"的推荐，让 Agent 只需要确认而非分析。

### 6.4 监管与合规

**AI 自主交易的法律主体问题。** 在大多数法域，AI 不具有法律主体地位，不能独立签订合同或持有财产。这意味着 Agent 的交易在法律上仍需要追溯到一个自然人或法人。x402 协议通过"人类授权 + AI 执行"的模式绕过了这个问题（Agent 使用人类授权的支付凭证），但随着 Agent 自主性增强，法律框架的更新是迟早的事。

**跨境 AI 交易的数据合规。** 一个中国的 Agent 购买美国卖家的模型服务，数据如何跨境？中国的《数据安全法》和《个人信息保护法》、欧盟的 GDPR、美国的各州隐私法，都对数据跨境有严格限制。AIMart 需要在架构层面支持数据本地化存储和处理。

**算力期货等金融衍生品监管。** 上海已启动算力期货研发，算力正在金融化。如果 AIMart 上的算力交易发展出期货、期权等衍生品，将涉及金融牌照和监管合规。

## 七、关键路径与里程碑

### 7.1 三阶段路线图

**Phase 1（0-12 个月）：协议整合 + 技能市场 MVP**

核心目标：证明"AI 可以在市场上自主购买能力"。

关键动作：
- 发布 AI 能力搜索协议规范，开源，吸引社区讨论和迭代
- 对接 2-3 个主流 Agent 框架（LangChain、CrewAI、Dify）作为集成试点
- 上线技能市场和模型市场（先不做专家和算力），商品来源优先对接 HuggingFace 等现有平台
- 实现基础版 x402 微支付集成，支持 Agent 自主小额购买
- 前期卖家零佣金，降低上架摩擦
- 上线基础版沙箱试用环境和效果回传机制

成功指标：月活跃 Agent 数 > 1000，月交易量 > 10 万笔，卖家数 > 500

**Phase 2（12-24 个月）：支付体系 + 专家市场**

核心目标：建立完整的 AI 支付基础设施，扩展商品品类。

关键动作：
- 集成 ACP 和 AP2 协议，支持"Agent 代理人类支付"和"加密签名授权"
- 上线分层授权机制（全自动/事后通知/事前审批/人工确认）
- 上线预算管理仪表盘和异常监控
- 上线专家市场，引入领域认证机制
- 上线算力市场，对接主流云 GPU 供应商
- 发布动态信任评分系统（基准测试 + 效果回传 + Agent 间口碑）

成功指标：月活跃 Agent 数 > 10 万，月交易额 > 1000 万元，四类商品全覆盖

**Phase 3（24-36 个月）：Agent 生态网络**

核心目标：从交易平台升级为 Agent 服务网络。

关键动作：
- 上线 A2A 协议集成，支持 Agent 间自主协商和协作
- 推出跨组织 Agent 联邦机制，Agent 可以跨企业发现和协作
- 建立第三方认证生态，引入独立评估机构
- 启动 Agent 质量标准（SLA 式协议），卖家可以承诺性能保证
- 探索算力期货等金融化产品
- 国际化扩展，支持多法域合规

成功指标：月活跃 Agent 数 > 100 万，年交易额 > 10 亿元，覆盖 10+ 国家/地区

### 7.2 护城河构建

AIMart 的护城河与淘宝一脉相承——不是商品本身，而是三个层次的锁定：

**流量护城河：接入主流 Agent 框架。** 当 AIMart 成为 LangChain、CrewAI、Dify 等框架的默认能力扩展插件时，所有使用这些框架构建的 Agent 都自动成为 AIMart 的潜在买家。框架集成的网络效应一旦建立，后来者需要说服每个框架单独切换，切换成本极高。

**信任护城河：能力认证 + 效果回传 + 担保结算。** 动态信任评分是 AIMart 最核心的差异化机制——它让买卖双方建立可量化的信任关系，而不依赖人类的主观评价。评分数据和效果回传数据沉淀越多，信任体系越精准，后来者即使复制了协议和架构，也无法复制数据资产。

**基础设施护城河：AI 支付系统 + 标准化搜索协议 + 试用沙箱。** 这三者分别对应交易的三个关键环节——"怎么找到"、"怎么验证"、"怎么付钱"。其中，标准化搜索协议的壁垒最高：谁定义了"AI 如何描述需求、市场如何返回结果"的标准，谁就掌握了 AI 交易的入口。

### 7.3 终局愿景

AIMart 的终局不是一个市场，而是一个 **Agent 服务网络（Agent Service Network）**。

在今天的互联网中，微服务架构让软件组件可以通过标准化 API 互相发现和调用。在 AIMart 的终局中，AI Agent 取代了微服务的位置——每个 Agent 是一个自主节点，拥有自己的能力、预算和决策逻辑。Agent 之间通过 A2A 协议自主发现、评估、协商、协作，形成一个网状的自组织网络。

在这个网络中：
- 一个擅长写代码的 Agent 可以自主"雇佣"一个擅长做设计的 Agent
- 一个 Agent 发现自己的数学能力不足时，可以自主购买一个数学推理模型
- 多个 Agent 可以组成临时团队协作完成复杂任务，任务完成后自动结算和评价
- 整个过程人类只出了第一句需求

这不是科幻。AutoGPT、CrewAI、OpenClaw 等多 Agent 框架已经在往这个方向推进。AIMart 的角色，是成为这个网络中的**发现层、信任层和结算层**——让 Agent 不只是能协作，而是能在协作中自主交易。

**价值创造的转移：** 在 Agent 服务网络中，价值创造将从个体 Agent 的能力转向生态的网络效应。一个单独的 Agent 再强，也无法覆盖所有需求；但一个接入网络的 Agent，可以在需要时自主获取任何能力。网络越大，每个节点的有效能力越强——这就是网络效应的飞轮。

AIMart 要做的，就是启动这个飞轮。

## 一、参与者定义

AIMart 生态中存在 7 类参与者，每类参与者的动机、行为模式和系统交互方式各不相同。

### 1.1 参与者总览

| ID | 参与者 | 定义 | 核心动机 | 是否为系统内主体 |
|----|--------|------|---------|----------------|
| P-01 | Agent Owner | Agent 的所有者（人类或组织），为 Agent 提供预算和策略 | 让 Agent 高效完成任务，控制成本 | 是 |
| P-02 | AI Agent | 自主执行任务的 AI 系统，是市场的主要买家 | 获取能力以完成任务 | 是（核心） |
| P-03 | Capability Provider | 能力商品卖家，提供模型/技能/专家/算力 | 出售能力获取收入 | 是 |
| P-04 | Platform Operator | AIMart 平台运营方 | 收取佣金和增值服务费 | 是 |
| P-05 | Certifier | 第三方认证机构，验证能力商品质量 | 提供认证服务获取认证费 | 是 |
| P-06 | Facilitator | 支付结算中间方（x402 架构角色），验证支付并代理链上结算 | 收取结算服务费 | 是 |
| P-07 | Regulator | 监管机构，监督市场合规运营 | 维护市场秩序和消费者权益 | 否（外部） |

### 1.2 参与者详细定义

#### P-01 Agent Owner（Agent 所有者）

```
唯一标识：owner_id (string, UUID)
属性：
  - name: 组织/个人名称
  - type: individual | enterprise | government
  - kyc_status: pending | verified | rejected
  - jurisdiction: 法域（CN/US/EU/...）
  - budget_pools: 关联的预算池列表
  - agents: 关联的 Agent 列表
  - created_at: 注册时间
  - risk_level: low | medium | high

行为边界：
  ✓ 创建和管理 Agent
  ✓ 设定预算池和消费策略
  ✓ 审批/拒绝 Agent 的大额交易请求
  ✓ 查看 Agent 的交易历史和效果报告
  ✓ 暂停/终止 Agent 的交易权限
  ✗ 代替 Agent 做购买决策（Agent 自主决策）
  ✗ 修改已完成的交易记录

约束：
  - 一个 Owner 可以拥有多个 Agent
  - Owner 对其 Agent 的所有交易承担法律责任
  - Owner 的 KYC 状态影响其 Agent 的交易权限上限
```

#### P-02 AI Agent（AI 代理）

```
唯一标识：agent_id (string, UUID)
属性：
  - name: Agent 名称
  - owner_id: 所属 Owner
  - framework: langchain | crewai | autogen | dify | coze | custom
  - capability_scope: Agent 当前已具备的能力范围
  - trust_score: 动态信任评分 (0-100)
  - spending_authority: 当前消费授权级别
  - status: active | suspended | terminated
  - created_at: 创建时间
  - last_active_at: 最后活跃时间

行为边界：
  ✓ 在预算池范围内自主搜索和购买能力
  ✓ 试用沙箱中的能力商品
  ✓ 回传使用效果评价（结构化数据）
  ✓ 通过 A2A 与其他 Agent 协商
  ✓ 在授权范围内自主完成微支付
  ✗ 超出预算池总额消费
  ✗ 绕过分层授权机制（越权交易）
  ✗ 修改自身 trust_score
  ✗ 访问其他 Agent 的私有上下文数据
  ✗ 执行未经验证的技能代码（非沙箱）

约束：
  - Agent 不具有法律主体地位，交易法律效果归属于 Owner
  - Agent 的所有交易行为必须可追溯至 Owner
  - Agent 的 trust_score 由平台基于历史行为动态计算，不可篡改
  - Agent 被暂停后，所有进行中的交易进入冻结状态
```

#### P-03 Capability Provider（能力提供方）

```
唯一标识：provider_id (string, UUID)
属性：
  - name: 提供方名称
  - type: individual | enterprise | research_org | open_source_community
  - kyc_status: pending | verified | rejected
  - jurisdiction: 法域
  - listing_count: 上架商品数
  - overall_rating: 综合评分 (0-5)
  - certification_status: uncertified | certified | premium_certified
  - dispute_count: 争议次数
  - created_at: 注册时间

行为边界：
  ✓ 上架能力商品（需通过平台验证）
  ✓ 设定商品定价和 SLA
  ✓ 更新商品版本（需重新验证）
  ✓ 查看商品的使用统计和评价

  ✗ 收集买方 Agent 的上下文数据（未经授权）
  ✗ 对评价数据进行刷分操作
  ✗ 在未通知的情况下下架有活跃订阅的商品

约束：
  - 上架商品必须提供基准测试结果
  - 商品能力声明与实际表现的偏差超过阈值时自动降级

  - 提供方需缴纳保证金（金额与商品定价等级挂钩）
```

### 3.2 领域详细定义

#### 商品域（Catalog Domain）

```
领域 ID：D-CATALOG
```

#### 交易域（Exchange Domain）

```
领域 ID：D-EXCHANGE

核心实体：

状态机（Order）：

边界：

```

#### 支付域（Payment Domain）

```
领域 ID：D-PAYMENT
职责：管理预算、授权、结算、担保交易全流程

  - Authorization：消费授权
  - Transaction：支付交易
  - EscrowAccount：担保账户

子领域：
  D-PAYMENT-BUDGET：预算管理
  D-PAYMENT-AUTH：授权管理
  D-PAYMENT-SETTLE：结算执行（x402/ACP/AP2/MPP）

边界：
  - 入口：交易域发起支付请求 / Owner 充值预算 / Owner 调整策略
```

#### 信任域（Trust Domain）

```
领域 ID：D-TRUST
职责：管理动态信任评分、效果回传、评价、争议处理

核心实体：
```

## 四、参与者-领域交互边界

### 4.1 交互矩阵

| 参与者 \ 领域 | 商品域 | 交易域 | 支付域 | 信任域 | 搜索域 | 身份域 | 审计域 |
|-------------|:------:|:------:|:------:|:------:|:------:|:------:|:------:|
| Agent Owner | R | R(所属) | CRUD | R | — | CRUD | R(所属) |
| AI Agent | R | RW | R(受限) | RW | RW | R(自身) | — |
| Provider | CRUD(自身) | R(自身) | R(自身) | R(自身) | — | CRUD(自身) | R(自身) |
| Platform | 全部 | 全部 | R+仲裁 | 全部 | R | 全部 | 全部 |
| Certifier | RW(认证) | — | — | RW | — | R | R |
| Facilitator | — | R(结算) | RW(结算) | — | — | R | R |

### 4.2 跨域交互规则

1. **商品域 → 搜索域**：商品上架/更新时，自动同步到搜索索引；下架时自动从索引移除
2. **搜索域 → 交易域**：Agent 基于搜索结果发起购买，搜索结果作为订单的匹配依据
3. **交易域 → 支付域**：订单创建后触发支付请求，支付结果决定订单状态流转
4. **交易域 → 信任域**：交易完成后 Agent 回传效果，触发信任评分更新
5. **信任域 → 搜索域**：信任评分变化影响搜索排序权重
6. **信任域 → 商品域**：信任评分低于阈值时自动触发商品下架
7. **支付域 → 审计域**：所有结算操作必须写入审计日志
8. **身份域 → 所有域**：所有操作必须经过身份验证和授权检查

### 4.3 禁止的交互

1. Agent **不可**直接修改预算池（只有 Owner 可以）
2. Provider **不可**直接修改评价数据（只有 Agent 回传和平台仲裁可以）
3. Facilitator **不可**访问业务内容数据（只能看到结算相关信息）
4. 任何参与者 **不可**跨过身份域直接操作其他域
5. Agent **不可**在未搜索匹配的情况下直接创建订单（必须经过搜索域）

# v2.0 落地补充：法律主体、Agent 成熟度与 Codex 边界

## 1. 法律主体边界

AI Agent 不是法律主体。系统实现时必须满足：

```text
1. Agent 必须绑定 Agent Owner。
2. Agent 不能独立签订合同。
3. Agent 不能独立持有资产。
4. Agent 的所有支付、订单、调用都必须追溯到 Owner 或 Organization。
5. Agent 创建订单草案可以自动，但正式订单和大额支付必须由 Owner 授权。
```

建议在数据模型中体现：

```text
AgentIdentity.owner_id 必填
AgentIdentity.organization_id 可选但企业场景建议必填
Order.legal_buyer_id 必填
PaymentMock.budget_owner_id 必填
```

## 2. Agent 成熟度边界

为了应对生产环境 Agent 成熟度不足的问题，MVP 必须增加 Agent 成熟度分层：

```yaml
agent_maturity_levels:
  M0:
    name: "未验证 Agent"
    allowed:
      - "search"
      - "read"
    blocked:
      - "quote"
      - "order"
      - "execute"
  M1:
    name: "沙箱验证 Agent"
    allowed:
      - "search"
      - "read"
      - "compare"
      - "sandbox_trial"
    blocked:
      - "real_execution"
      - "payment"
  M2:
    name: "受控生产 Agent"
    allowed:
      - "quote_request"
      - "low_risk_execution_with_budget"
    requires:
      - "owner_bound"
      - "budget_bound"
      - "audit_enabled"
  M3:
    name: "企业认证生产 Agent"
    allowed:
      - "preapproved_medium_risk_execution"
      - "organization_budget"
    requires:
      - "organization_verified"
      - "approval_policy_configured"
      - "production_usage_history"
```

MVP 默认：

```text
新 Agent 默认为 M0。
只有 M2 及以上 Agent 可以在预算内调用低风险能力。
中风险能力需要预授权。
高风险能力必须人工审批。
```

## 3. Codex 实现要求

```text
1. AgentIdentity 必须包含 maturity_level。
2. 规则引擎必须检查 maturity_level。
3. 成熟度不足时返回 AGENT_MATURITY_REQUIRED。
4. 成熟度检查结果必须写审计日志。
5. 不得允许匿名 Agent 发起交易。
```

## 一、交易规则

### 1.1 商品上架规则

| 规则 ID | 规则内容 | 适用对象 | 违规后果 |
|---------|---------|---------|---------|

| TR-002 | 上架商品必须提供至少一项基准测试结果 | Provider | 拒绝上架 |
| TR-003 | 能力声明中的性能指标不得高于基准测试结果的 110%（防止过度承诺） | Provider | 自动降级声明或拒绝上架 |
| TR-004 | 定价必须明确（按量/按时/订阅/免费），不得设置隐性费用 | Provider | 下架 + 保证金扣除 |

| TR-006 | 技能类商品必须通过沙箱安全扫描（无恶意代码、无数据外泄行为） | Provider | 拒绝上架 |
| TR-007 | 专家类商品必须声明知识库更新频率和最后更新时间 | Provider | 拒绝上架 |
| TR-008 | 算力类商品必须声明可用性承诺（SLA）和最大并发数 | Provider | 拒绝上架 |
| TR-009 | 商品版本更新必须重新提交验证，验证期间旧版本可继续服务 | Provider | 旧版本自动下架 |

### 1.2 交易流程规则

| 规则 ID | 规则内容 | 适用阶段 |
|---------|---------|---------|
| TR-011 | Agent 必须通过搜索域发起能力需求，不得绕过搜索直接调用 | 搜索 |

### 3.2 风险应对措施

#### R-001 恶意技能数据窃取

```
预防：
  - 技能上架前强制沙箱安全扫描
  - 技能运行时网络隔离（仅允许与声明的外部服务通信）
  - Agent 上下文数据默认不传递给技能，需显式授权

检测：
  - 运行时行为监控：检测异常网络请求、异常数据访问
  - Agent 消费模式分析：检测被诱导消费的模式

响应：
  - 自动终止恶意技能运行
  - 冻结卖家账户
  - 通知所有使用该技能的 Agent Owner
  - 启动安全审计
```

#### R-003 Agent 被诱导消费

```
预防：
  - 分层授权机制（L0-L3）
  - 单卖家消费集中度监控
  - 卖家能力声明验证（不得超过基准测试 110%）

检测：
  - 消费模式异常检测
  - Agent 决策路径审计

响应：
  - 触发异常规则自动暂停交易
  - 通知 Owner 确认
  - 对诱导消费的卖家进行处罚
```

#### R-004 卖家虚报能力

```
预防：
  - 基准测试结果强制提交
  - 能力声明自动校验（声明值 vs 基准测试值）
  - 担保交易机制

检测：
  - Agent 效果回传与卖家声明的偏差分析
  - 偏差超过 20% 自动触发调查

响应：
  - 信任评分自动下调
  - 严重虚报：商品下架 + 保证金扣除
  - 连续 3 次虚报：卖家封禁
```

### 5.3 SLA 违约处理

```

4. 通知：违约信息通知买方 Owner 和卖家
```

## 一、AgentCard 总体规范

### 1.1 设计原则

- **机器可读**：所有字段使用 JSON Schema 定义，AI Agent 可直接解析，无需自然语言理解
- **结构化声明**：能力描述不是文案，而是可验证的结构化声明——每个性能指标都可以与基准测试结果对照
- **分层设计**：基础层（所有商品共有）+ 扩展层（按商品类型特化），避免冗余同时保持灵活性
- **版本化**：AgentCard 自身版本化，支持 Agent 指定所需版本

### 1.2 Schema 版本

```
agentcard_schema_version: "1.0"
规范 URI: https://aimart.dev/schemas/agentcard/v1.0
```

## 四、AgentCard 注册与发现

### 4.1 注册流程

```
1. Provider 创建 AgentCard（JSON 格式）
2. 提交至 AIMart 商品域 API: POST /api/v1/catalog/items
3. 平台自动验证：
   a. Schema 合规性检查（必须符合 v1.0 规范）
   b. 能力声明 vs 基准测试偏差检查（≤ 110%）
   c. 安全扫描（技能类必须通过）
   d. 定价合理性检查（不得与同类商品差异超过 10 倍，防止刷单）
4. 验证通过 → 商品上架，AgentCard 索引至搜索域
5. 验证失败 → 返回具体失败原因，Provider 修改后重新提交
6. 认证（可选）：Provider 可申请第三方认证，提升信任评分
```

### 4.3 版本管理

```
VERSION-001: AgentCard 每次更新创建新版本，旧版本保留 90 天
VERSION-002: Agent 可在请求中指定所需版本（默认最新）
VERSION-003: 重大变更（能力声明下调、定价上涨、接口不兼容）需标记为 major version
VERSION-004: 订阅制商品的 AgentCard 重大变更需提前 7 天通知已订阅 Agent
VERSION-005: 已下架商品的 AgentCard 保留 365 天（供审计和争议追溯）
```

# AIMart 日志与审计文件：确保每一步可追溯

> 版本：v1.0 | 2026-06-07 | 状态：设计阶段

---

## 一、设计原则

### 1.1 核心原则

| 原则 | 说明 |
|------|------|
| **全程可追溯** | 从 Agent 搜索到最终结算，每一步操作都产生审计日志 |
| **不可篡改** | 审计日志采用追加写入 + 哈希链校验，任何篡改都可检测 |
| **最小必要** | 日志只记录业务操作和合规必需的数据，不记录业务内容（如输入文本） |
| **分层存储** | 热数据（7天）→ 温数据（90天）→ 冷数据（365天），按访问频率分存储层 |
| **隐私保护** | Agent 上下文数据不记入日志，只记录数据元信息（类型、大小、敏感度） |

### 1.2 日志生命周期

```
生成 → 采集 → 验证 → 存储 → 索引 → 查询 → 归档 → 销毁
 0ms   <1s    <1s    <1s    <5s    实时   按策略   按法规
```

---

## 二、日志分类与 Schema

### 2.1 日志分类

| 日志类别 | 日志 ID 前缀 | 保留期限 | 存储层 | 用途 |
|---------|-------------|---------|--------|------|
| 身份日志 | LOG-ID | 365 天 | 冷 | 身份操作审计 |
| 商品日志 | LOG-CT | 365 天 | 冷 | 商品上架/更新/下架审计 |
| 搜索日志 | LOG-SR | 30 天 | 温 | 搜索行为分析、推荐优化 |
| 交易日志 | LOG-EX | 365 天 | 温 | 交易全流程审计 |
| 支付日志 | LOG-PY | 365 天 | 冷 | 支付结算审计、合规 |
| 信任日志 | LOG-TR | 365 天 | 冷 | 信任评分变更审计 |
| 安全日志 | LOG-SC | 365 天 | 冷 | 安全事件审计 |
| 系统日志 | LOG-SY | 90 天 | 温 | 系统运行监控 |

### 2.2 通用日志 Schema

所有日志条目共享以下基础结构：

```json
{
```

### 2.3 哈希链机制

```python
# 日志哈希链伪代码
class AuditLogEntry:
    def compute_hash(self):
        payload = f"{self.log_id}|{self.timestamp}|{self.actor_id}|{self.action}|{self.data_hash}|{self.previous_hash}"
        return sha256(payload.encode()).hexdigest()

# 验证链完整性
def verify_chain(entries: list[AuditLogEntry]) -> bool:
    for i in range(1, len(entries)):
        if entries[i].previous_hash != entries[i-1].compute_hash():
            return False  # 链断裂 = 篡改嫌疑
    return True

# 每 10000 条日志生成一个检查点（checkpoint）
# 检查点包含：起始/结束 log_id、起始/结束 hash、条目数、整体 merkle root
# 检查点写入区块链（可选，用于更高安全等级）
```

## 五、审计场景

### 5.1 典型审计场景

#### 场景一：Agent 被诱导消费调查

```
触发：Owner 报告 Agent 异常消费
查询路径：
  1. LOG-PY-ANOMALY → 找到异常检测记录
  2. LOG-EX-ORDER-CREATE → 找到所有相关订单
  3. LOG-SR-QUERY → 检查搜索是否被操纵（搜索结果是否异常偏向某卖家）
  4. LOG-EX-EFFECT-REPORT → 检查效果回传是否正常（是否被篡改跳过）
  5. LOG-SC-FRAUD-DETECT → 检查是否有刷分/操纵行为
  6. 汇总：确认是否为诱导消费，确定责任方，执行赔偿
```

#### 场景二：卖家虚假声明调查

```
触发：Agent 效果回传与卖家声明偏差持续超过 20%
查询路径：
  1. LOG-TR-SCORE-UPDATE → 信任评分变化历史
  2. LOG-EX-EFFECT-REPORT → 所有效果回传记录
  3. LOG-CT-LIST → 商品上架时的声明数据
  4. 对比声明值与效果回传的实际值
  5. LOG-EX-DISPUTE → 相关争议记录
  6. 汇总：确认虚假声明程度，执行下架和保证金扣除
```

#### 场景三：沙箱逃逸安全事件

```
触发：沙箱监控检测到违规行为
查询路径：
  1. LOG-SC-SANDBOX-VIOLATION → 违规详情
  2. LOG-EX-ORDER-CREATE → 使用该技能的所有订单
  3. LOG-EX-DELIVERY → 检查是否有数据泄露
  4. LOG-SC-DATA-LEAK → 数据泄露嫌疑检查
  5. LOG-ID-AGENT-TERMINATE → 受影响 Agent 处理
  6. 汇总：评估影响范围，通知受影响 Owner，封禁 Provider
```

#### 场景四：合规审计（监管机构）

```
触发：监管机构依法令要求审计
查询路径：
  1. GET /api/v1/audit/checkpoint/{date} → 获取检查点
  2. POST /api/v1/audit/verify → 验证日志完整性
  3. 按需求查询特定时间范围、特定参与者的日志
  4. 验证关键业务流程合规性：
     - 所有交易是否有对应授权
     - 支付结算是否符合法规
     - 跨境数据传输是否合规
     - Agent 操作是否在授权范围内
```

## 六、合规与保留策略

### 6.1 数据保留

| 数据类型 | 保留期限 | 到期处理 | 法规依据 |
|---------|---------|---------|---------|
| 交易记录 | 5 年 | 匿名化归档 | 电商法规 |
| 支付记录 | 5 年 | 匿名化归档 | 金融法规 |
| 身份认证记录 | 5 年 | 删除 | 隐私法规 |
| 审计日志 | 365 天（热） → 5 年（冷） | 归档 | 合规要求 |
| 搜索日志 | 30 天 | 删除 | 最小必要原则 |
| 安全事件日志 | 5 年 | 匿名化归档 | 安全法规 |
| 争议记录 | 5 年 | 匿名化归档 | 电商法规 |

### 6.2 数据脱敏规则

```
DESENSITIZE-001: Agent 输入/输出内容不记入日志，只记元信息（大小、类型、敏感度）
DESENSITIZE-002: IP 地址存储时使用 SHA-256 哈希，不存原始 IP
DESENSITIZE-003: 预算余额信息对非 Owner 参与者不可见
DESENSITIZE-004: 争议证据中的业务内容按需提供，审计日志只记哈希
DESENSITIZE-005: 日志归档时，Agent 的 framework 和能力范围信息做匿名化处理
DESENSITIZE-006: 跨境日志查询必须经过双重合规验证（源法域 + 目标法域）
```

### 6.3 审计报告

```
自动生成周期：
  - 日报：异常事件汇总、交易量统计
  - 周报：信任评分变动、争议处理统计、安全事件统计
  - 月报：合规状态、SLA 达标率、资金流向分析
  - 季报：平台运营审计报告（提交监管机构）

报告访问权限：
  - 日报/周报：Platform 运维团队
  - 月报：Platform 管理层 + 参与者（自身数据）
  - 季报：Platform 管理层 + Regulator
```

```python
from __future__ import annotations

from dataclasses import dataclass, field
from enum import Enum
from typing import Any, Callable
import structlog

logger = structlog.get_logger()


class RuleSeverity(str, Enum):
    """规则违规严重级别"""
    INFO = "info"          # 记录但不阻止
    WARNING = "warning"    # 警告但不阻止
    BLOCK = "block"        # 阻止操作
    SUSPEND = "suspend"    # 暂停参与者


class RuleCategory(str, Enum):
    """规则类别"""
    TRADING = "trading"       # 交易规则（TR-xxx）
    BUDGET = "budget"         # 预算规则
    SECURITY = "security"     # 安全规则（SEC-xxx）
    SLA = "sla"              # SLA 规则
    PRICING = "pricing"       # 定价规则（PRICING-xxx）


@dataclass
class RuleContext:
    """规则评估上下文——携带所有规则可能需要的运行时数据"""
    # 操作者
    actor_type: str               # agent | owner | provider | platform
    actor_id: str
    owner_id: str | None = None

    # 操作
    operation: str                # order_create | item_list | payment_settle | ...
    target_type: str | None = None
    target_id: str | None = None

    # 商品信息（商品相关规则需要）
    item_type: str | None = None  # model | skill | expert | compute
    item_id: str | None = None
    agentcard: dict | None = None

    # 交易信息（交易相关规则需要）
    order_id: str | None = None
    amount_cny: float | None = None
    pricing_model: str | None = None

    # 预算信息（预算相关规则需要）
    budget_pool_id: str | None = None
    budget_balance: float | None = None
    budget_daily_spent: float | None = None
    budget_daily_max: float | None = None
    budget_weekly_spent: float | None = None
    budget_weekly_max: float | None = None
    budget_monthly_spent: float | None = None
    budget_monthly_max: float | None = None
    per_call_max: float | None = None
    agent_daily_spent: float | None = None
    agent_daily_max: float | None = None

    # 效果回传（信任相关规则需要）
    effect_score: int | None = None
    success: bool | None = None
    actual_latency_ms: int | None = None
    declared_latency_ms: int | None = None
    declaration_accuracy: float | None = None

    # 授权信息
    spending_authority_level: str | None = None  # L0 | L1 | L2 | L3

    # 安全信息
    security_scan_result: str | None = None  # clean | warning | failed
    sandbox_verified: bool | None = None
    data_sensitivity: str | None = None      # public | internal | confidential | restricted


@dataclass
class RuleResult:
    """单条规则的评估结果"""
    rule_id: str
    rule_name: str
    category: RuleCategory
    passed: bool
    severity: RuleSeverity
    message: str
    data: dict[str, Any] = field(default_factory=dict)


@dataclass
class RuleEvaluationResult:
    """规则引擎整体评估结果"""
    results: list[RuleResult] = field(default_factory=list)
    blocked: bool = False
    blocked_by: list[str] = field(default_factory=list)
    warnings: list[str] = field(default_factory=list)
    audit_events: list[dict] = field(default_factory=list)

    def add(self, result: RuleResult) -> None:
        self.results.append(result)
        if not result.passed:
            if result.severity == RuleSeverity.BLOCK:
                self.blocked = True
                self.blocked_by.append(result.rule_id)
            elif result.severity == RuleSeverity.SUSPEND:
                self.blocked = True
                self.blocked_by.append(result.rule_id)
            elif result.severity == RuleSeverity.WARNING:
                self.warnings.append(f"{result.rule_id}: {result.message}")


class Rule:
    """单条规则的抽象基类"""

    rule_id: str = ""
    rule_name: str = ""
    category: RuleCategory = RuleCategory.TRADING
    severity: RuleSeverity = RuleSeverity.BLOCK
    applies_to_operations: list[str] = []  # 空列表 = 适用于所有操作

    def applies(self, context: RuleContext) -> bool:
        """判断此规则是否适用于当前上下文"""
        if not self.applies_to_operations:
            return True
        return context.operation in self.applies_to_operations

    async def evaluate(self, context: RuleContext) -> RuleResult:
        """评估规则，子类必须实现"""
        raise NotImplementedError


class RulesEngine:
    """规则引擎——加载所有规则，按上下文评估，返回结果"""

    def __init__(self) -> None:
        self._rules: list[Rule] = []
        self._logger = structlog.get_logger()

    def register(self, rule: Rule) -> None:
        self._rules.append(rule)
        self._logger.info("rule_registered", rule_id=rule.rule_id, rule_name=rule.rule_name)

    async def evaluate(self, context: RuleContext) -> RuleEvaluationResult:
        """评估所有适用规则"""
        result = RuleEvaluationResult()

        for rule in self._rules:
            if not rule.applies(context):
                continue

            try:
                rule_result = await rule.evaluate(context)
                result.add(rule_result)

                if not rule_result.passed:
                    self._logger.warning(
                        "rule_violation",
                        rule_id=rule.rule_id,
                        actor_id=context.actor_id,
                        operation=context.operation,
                        message=rule_result.message,
                    )
            except Exception as e:
                self._logger.error(
                    "rule_evaluation_error",
                    rule_id=rule.rule_id,
                    error=str(e),
                )
                # 规则评估出错时保守处理：阻止操作
                result.add(RuleResult(
                    rule_id=rule.rule_id,
                    rule_name=rule.rule_name,
                    category=rule.category,
                    passed=False,
                    severity=RuleSeverity.BLOCK,
                    message=f"Rule evaluation error: {str(e)}",
                ))

        return result
```

```python
    """TR-003: 能力声明不得高于基准测试结果的 110%"""
    rule_id = "TR-003"
    rule_name = "declaration_overpromise_check"
    category = RuleCategory.TRADING
    severity = RuleSeverity.BLOCK
    applies_to_operations = ["item_list"]

    async def evaluate(self, context: RuleContext) -> RuleResult:
        if context.agentcard is None:
            return RuleResult(self.rule_id, self.rule_name, self.category, False, self.severity, "No AgentCard")

        benchmarks = context.agentcard.get("performance_declaration", {}).get("benchmarks", [])
        violations = []
        for b in benchmarks:
            declared = b.get("declared_value")
            verified = b.get("verified_value")
            if declared is not None and verified is not None and verified > 0:
                ratio = declared / verified
                if ratio > 1.10:
                    violations.append({
                        "benchmark": b.get("benchmark_name"),
                        "metric": b.get("metric"),
                        "declared": declared,
                        "verified": verified,
                        "ratio": round(ratio, 3),
                    })

        passed = len(violations) == 0
        return RuleResult(
            rule_id=self.rule_id,
            rule_name=self.rule_name,
            category=self.category,
            passed=passed,
            severity=self.severity,
            message=f"Performance declaration exceeds 110% of verified value for {len(violations)} metrics" if violations else "",
            data={"violations": violations},
        )
```

```python
    rule_name = "spending_authority_level"
    category = RuleCategory.BUDGET

        (0.01, "L0", "全自动"),
        (1.00, "L1", "事后通知"),
        (100.00, "L2", "事前审批"),
        (float("inf"), "L3", "人工确认"),

        required_level = "L3"
        required_desc = "人工确认"

        level_order = {"L0": 0, "L1": 1, "L2": 2, "L3": 3}

        return RuleResult(
            rule_id=self.rule_id,
            rule_name=self.rule_name,
            category=self.category,
            passed=passed,
            severity=self.severity if not passed else RuleSeverity.INFO,
            message=f"Authorization level {required_level} ({required_desc}) required for amount {context.amount_cny} CNY" if not passed else f"Authorization level {required_level} sufficient",
            data={
                "required_level": required_level,
                "current_level": current_level,
                "amount": context.amount_cny,
                "description": required_desc,
```

## 二、Schema 校验器

```python
# src/aimart/catalog/validator.py

from __future__ import annotations

import json
from pathlib import Path
from typing import Any

import jsonschema
from jsonschema import Draft202012Validator, ValidationError
import structlog

logger = structlog.get_logger()

# JSON Schema 文件路径
SCHEMAS_DIR = Path(__file__).parent.parent.parent.parent / "schemas"

# 商品类型 → 扩展层 Schema 映射
EXTENSION_SCHEMAS = {
    "model": "agentcard_model_v1.json",
    "skill": "agentcard_skill_v1.json",
    "expert": "agentcard_expert_v1.json",
    "compute": "agentcard_compute_v1.json",
}


class SchemaValidationError:
    """Schema 校验错误"""

    def __init__(self, path: str, message: str, schema_id: str | None = None):
        self.path = path
        self.message = message
        self.schema_id = schema_id

    def to_dict(self) -> dict:
        return {
            "path": self.path,
            "message": self.message,
            "schema_id": self.schema_id,
        }


class AgentCardSchemaValidator:
    """AgentCard JSON Schema 校验器"""

    def __init__(self) -> None:
        self._base_validator: Draft202012Validator | None = None
        self._extension_validators: dict[str, Draft202012Validator] = {}
        self._load_schemas()

    def _load_schemas(self) -> None:
        """加载所有 JSON Schema 文件"""
        base_schema_path = SCHEMAS_DIR / "agentcard_base_v1.json"
        if base_schema_path.exists():
            with open(base_schema_path) as f:
                base_schema = json.load(f)
            self._base_validator = Draft202012Validator(base_schema)

        for item_type, schema_file in EXTENSION_SCHEMAS.items():
            schema_path = SCHEMAS_DIR / schema_file
            if schema_path.exists():
                with open(schema_path) as f:
                    schema = json.load(f)
                self._extension_validators[item_type] = Draft202012Validator(schema)

    def validate(self, agentcard: dict[str, Any]) -> list[SchemaValidationError]:
        """校验 AgentCard：先基础层，再扩展层"""
        errors: list[SchemaValidationError] = []

        # 1. 基础层校验
        if self._base_validator:
            for error in sorted(self._base_validator.iter_errors(agentcard), key=lambda e: list(e.path)):
                errors.append(SchemaValidationError(
                    path=".".join(str(p) for p in error.path) or "root",
                    message=error.message,
                    schema_id="agentcard_base_v1",
                ))
        else:
            logger.warning("base_schema_not_loaded")

        # 2. 扩展层校验
        item_type = agentcard.get("identity", {}).get("item_type")
        if item_type and item_type in self._extension_validators:
            ext_validator = self._extension_validators[item_type]
            ext_data = agentcard.get(f"{item_type}_extension", {})
            for error in sorted(ext_validator.iter_errors(ext_data), key=lambda e: list(e.path)):
                errors.append(SchemaValidationError(
                    path=f"{item_type}_extension." + ".".join(str(p) for p in error.path),
                    message=error.message,
                    schema_id=EXTENSION_SCHEMAS[item_type],
                ))

        return errors
```

```python
# src/aimart/catalog/semantic_validator.py

from __future__ import annotations

from dataclasses import dataclass
from typing import Any

import structlog

logger = structlog.get_logger()


@dataclass
class SemanticValidationError:
    """语义校验错误"""
    rule_id: str
    field_path: str
    message: str
    severity: str  # error | warning

    def to_dict(self) -> dict:
        return {
            "rule_id": self.rule_id,
            "field_path": self.field_path,
            "message": self.message,
            "severity": self.severity,
        }


class AgentCardSemanticValidator:
    """AgentCard 语义校验器——校验 Schema 无法覆盖的业务规则"""

    def validate(self, agentcard: dict[str, Any]) -> list[SemanticValidationError]:
        errors: list[SemanticValidationError] = []

        errors.extend(self._validate_identity(agentcard))
        errors.extend(self._validate_capability_declaration(agentcard))
        errors.extend(self._validate_performance_declaration(agentcard))
        errors.extend(self._validate_pricing(agentcard))
        errors.extend(self._validate_delivery(agentcard))
        errors.extend(self._validate_trust(agentcard))
        errors.extend(self._validate_legal(agentcard))

        # 按商品类型做扩展校验
        item_type = agentcard.get("identity", {}).get("item_type")
        if item_type == "skill":
            errors.extend(self._validate_skill_extension(agentcard))
        elif item_type == "expert":
            errors.extend(self._validate_expert_extension(agentcard))
        elif item_type == "compute":
            errors.extend(self._validate_compute_extension(agentcard))

        return errors

    def _validate_identity(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        identity = card.get("identity", {})

        # item_type 必须是四种之一
        valid_types = {"model", "skill", "expert", "compute"}
        if identity.get("item_type") not in valid_types:
            errors.append(SemanticValidationError(
                rule_id="SEM-ID-001",
                field_path="identity.item_type",
                message=f"item_type must be one of {valid_types}, got '{identity.get('item_type')}'",
                severity="error",
            ))

        # 版本号格式检查（semver）
        version = identity.get("item_version", "")
        if version and not self._is_semver(version):
            errors.append(SemanticValidationError(
                rule_id="SEM-ID-002",
                field_path="identity.item_version",
                message=f"Version should follow semver (e.g., 2.3.1), got '{version}'",
                severity="warning",
            ))

        return errors

    def _validate_capability_declaration(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        cap = card.get("capability_declaration", {})

        # domains 不能为空
        if not cap.get("domains"):
            errors.append(SemanticValidationError(
                rule_id="SEM-CAP-001",
                field_path="capability_declaration.domains",
                message="domains must not be empty",
                severity="error",
            ))

        # task_types 至少有一个
        if not cap.get("task_types") or len(cap.get("task_types", [])) == 0:
            errors.append(SemanticValidationError(
                rule_id="SEM-CAP-002",
                field_path="capability_declaration.task_types",
                message="At least one task_type is required",
                severity="error",
            ))

        # 每个 task_type 必须有 input_schema 和 output_schema
        for i, tt in enumerate(cap.get("task_types", [])):
            if not tt.get("input_schema"):
                errors.append(SemanticValidationError(
                    rule_id="SEM-CAP-003",
                    field_path=f"capability_declaration.task_types[{i}].input_schema",
                    message=f"Task type '{tt.get('name', i)}' must have input_schema",
                    severity="error",
                ))
            if not tt.get("output_schema"):
                errors.append(SemanticValidationError(
                    rule_id="SEM-CAP-004",
                    field_path=f"capability_declaration.task_types[{i}].output_schema",
                    message=f"Task type '{tt.get('name', i)}' must have output_schema",
                    severity="error",
                ))

        # boundary_declaration 不能为空
        boundary = cap.get("boundary_declaration", {})
        if not boundary.get("in_scope") and not boundary.get("out_of_scope"):
            errors.append(SemanticValidationError(
                rule_id="SEM-CAP-005",
                field_path="capability_declaration.boundary_declaration",
                message="At least in_scope or out_of_scope must be declared",
                severity="warning",
            ))

        return errors

    def _validate_performance_declaration(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        perf = card.get("performance_declaration", {})

        # 必须有基准测试（TR-002）
        benchmarks = perf.get("benchmarks", [])
        if not benchmarks:
            errors.append(SemanticValidationError(
                rule_id="SEM-PERF-001",
                field_path="performance_declaration.benchmarks",
                message="At least one benchmark result is required (TR-002)",
                severity="error",
            ))

        # 声明值不得超过验证值的 110%（TR-003）
        for i, b in enumerate(benchmarks):
            declared = b.get("declared_value")
            verified = b.get("verified_value")
            if declared is not None and verified is not None and verified > 0:
                ratio = declared / verified
                if ratio > 1.10:
                    errors.append(SemanticValidationError(
                        rule_id="SEM-PERF-002",
                        field_path=f"performance_declaration.benchmarks[{i}]",
                        message=f"Declared value {declared} exceeds 110% of verified {verified} (ratio: {ratio:.2f}) (TR-003)",
                        severity="error",
                    ))

        # performance_constraints 必须有 latency 和 availability
        constraints = perf.get("performance_constraints", {})
        if not constraints.get("latency_p99_ms"):
            errors.append(SemanticValidationError(
                rule_id="SEM-PERF-003",
                field_path="performance_declaration.performance_constraints.latency_p99_ms",
                message="latency_p99_ms is required in performance_constraints",
                severity="error",
            ))
        if not constraints.get("availability_sla"):
            errors.append(SemanticValidationError(
                rule_id="SEM-PERF-004",
                field_path="performance_declaration.performance_constraints.availability_sla",
                message="availability_sla is required in performance_constraints",
                severity="error",
            ))

        return errors

    def _validate_pricing(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        pricing = card.get("pricing", {})

        # 定价模型必须是合法值
        valid_models = {"per_call", "per_token", "per_minute", "per_hour", "subscription", "free"}
        if pricing.get("model") not in valid_models:
            errors.append(SemanticValidationError(
                rule_id="SEM-PRICE-001",
                field_path="pricing.model",
                message=f"pricing.model must be one of {valid_models}",
                severity="error",
            ))

        # 定价详情必须与 model 匹配
        model = pricing.get("model", "")
        details = pricing.get("details", {})
        if model == "per_call" and not details.get("per_call"):
            errors.append(SemanticValidationError(
                rule_id="SEM-PRICE-002",
                field_path="pricing.details.per_call",
                message="per_call pricing requires per_call details",
                severity="error",
            ))
        elif model == "per_token" and not details.get("per_token"):
            errors.append(SemanticValidationError(
                rule_id="SEM-PRICE-003",
                field_path="pricing.details.per_token",
                message="per_token pricing requires per_token details",
                severity="error",
            ))
        elif model == "subscription" and not details.get("subscription"):
            errors.append(SemanticValidationError(
                rule_id="SEM-PRICE-004",
                field_path="pricing.details.subscription",
                message="subscription pricing requires subscription details",
                severity="error",
            ))

        # 免费商品也必须有 free_tier 或 details.free=True
        if model == "free" and not details.get("free_tier"):
            errors.append(SemanticValidationError(
                rule_id="SEM-PRICE-005",
                field_path="pricing.details.free_tier",
                message="free pricing should have free_tier details",
                severity="warning",
            ))

        return errors

    def _validate_delivery(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        delivery = card.get("delivery", {})

        # 交付方式必须是合法值
        valid_methods = {"api_call", "weight_download", "code_package", "instance"}
        if delivery.get("method") not in valid_methods:
            errors.append(SemanticValidationError(
                rule_id="SEM-DELIVERY-001",
                field_path="delivery.method",
                message=f"delivery.method must be one of {valid_methods}",
                severity="error",
            ))

        # api_call 必须有 endpoint
        if delivery.get("method") == "api_call" and not delivery.get("api_endpoint"):
            errors.append(SemanticValidationError(
                rule_id="SEM-DELIVERY-002",
                field_path="delivery.api_endpoint",
                message="api_call delivery requires api_endpoint",
                severity="error",
            ))

        # 支持的协议至少包含一个
        if not delivery.get("supported_protocols") or len(delivery.get("supported_protocols", [])) == 0:
            errors.append(SemanticValidationError(
                rule_id="SEM-DELIVERY-003",
                field_path="delivery.supported_protocols",
                message="At least one supported protocol is required",
                severity="error",
            ))

        return errors

    def _validate_trust(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        # 新上架商品 trust_score 由平台初始化，不在 AgentCard 中声明
        # 此处只校验结构合规
        return errors

    def _validate_legal(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        legal = card.get("legal", {})

        # data_handling.input_data_retention 必须声明
        data_handling = legal.get("data_handling", {})
        if not data_handling.get("input_data_retention"):
            errors.append(SemanticValidationError(
                rule_id="SEM-LEGAL-001",
                field_path="legal.data_handling.input_data_retention",
                message="input_data_retention must be declared",
                severity="error",
            ))

        # data_handling.input_data_usage 必须声明
        if not data_handling.get("input_data_usage"):
            errors.append(SemanticValidationError(
                rule_id="SEM-LEGAL-002",
                field_path="legal.data_handling.input_data_usage",
                message="input_data_usage must be declared",
                severity="error",
            ))

        return errors

    def _validate_skill_extension(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        ext = card.get("skill_extension", {})

        # 技能类型必须合法
        valid_types = {"tool", "workflow", "agent_template", "mcp_server"}
        if ext.get("skill_type") not in valid_types:
            errors.append(SemanticValidationError(
                rule_id="SEM-SKILL-001",
                field_path="skill_extension.skill_type",
                message=f"skill_type must be one of {valid_types}",
                severity="error",
            ))

        # 运行时环境必须声明
        runtime = ext.get("runtime", {})
        if not runtime.get("environment"):
            errors.append(SemanticValidationError(
                rule_id="SEM-SKILL-002",
                field_path="skill_extension.runtime.environment",
                message="Runtime environment is required for skills",
                severity="error",
            ))

        # 资源需求必须声明
        resources = ext.get("resource_requirements", {})
        if not resources:
            errors.append(SemanticValidationError(
                rule_id="SEM-SKILL-003",
                field_path="skill_extension.resource_requirements",
                message="Resource requirements must be declared for skills",
                severity="error",
            ))

        # 上下文数据访问必须声明
        context_access = ext.get("context_data_access", {})
        if context_access is None:
            errors.append(SemanticValidationError(
                rule_id="SEM-SKILL-004",
                field_path="skill_extension.context_data_access",
                message="context_data_access must be declared (even if requires_agent_context=false)",
                severity="error",
            ))

        return errors

    def _validate_expert_extension(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        ext = card.get("expert_extension", {})

        # 知识库更新频率必须声明

                rule_id="SEM-EXPERT-001",

                severity="error",
            ))

        # 司法管辖区必须声明
        domain = ext.get("domain", {})
        if not domain.get("jurisdictions_covered"):
            errors.append(SemanticValidationError(
                rule_id="SEM-EXPERT-002",
                field_path="expert_extension.domain.jurisdictions_covered",
                message="At least one jurisdiction must be declared",
                severity="error",
            ))

    def _validate_compute_extension(self, card: dict) -> list[SemanticValidationError]:
        errors = []
        ext = card.get("compute_extension", {})

        # GPU 类型必须声明
        instance = ext.get("instance_type", {})
        if not instance.get("gpu_type"):
            errors.append(SemanticValidationError(
                rule_id="SEM-COMPUTE-001",
                field_path="compute_extension.instance_type.gpu_type",
                message="GPU type is required for compute items",
                severity="error",
            ))

        # 可用性 SLA 必须声明
        availability = ext.get("availability", {})
        if not availability.get("sla_uptime_pct"):
            errors.append(SemanticValidationError(
                rule_id="SEM-COMPUTE-002",
                field_path="compute_extension.availability.sla_uptime_pct",
                message="SLA uptime percentage is required for compute items",
                severity="error",
            ))

        return errors

    @staticmethod
    def _is_semver(version: str) -> bool:
        """简单 semver 格式检查"""
        parts = version.split(".")
        if len(parts) != 3:
            return False
        try:
            int(parts[0])
            int(parts[1])
            # 第三部分可能有 -alpha 之类的后缀
            int(parts[2].split("-")[0])
            return True
        except ValueError:
            return False
```

```python
# src/aimart/catalog/validation_pipeline.py

from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any

from aimart.catalog.validator import AgentCardSchemaValidator, SchemaValidationError
from aimart.catalog.semantic_validator import AgentCardSemanticValidator, SemanticValidationError
import structlog

logger = structlog.get_logger()


@dataclass
class ValidationResult:
    """校验流水线整体结果"""
    valid: bool = True
    schema_errors: list[SchemaValidationError] = field(default_factory=list)
    semantic_errors: list[SemanticValidationError] = field(default_factory=list)
    security_scan_result: str = "pending"  # pending | clean | warning | failed
    security_scan_details: dict | None = None

    @property
    def all_errors(self) -> list[dict]:
        errors = [e.to_dict() for e in self.schema_errors]
        errors.extend([e.to_dict() for e in self.semantic_errors if e.severity == "error"])
        return errors

    @property
    def warnings(self) -> list[dict]:
        return [e.to_dict() for e in self.semantic_errors if e.severity == "warning"]


class AgentCardValidationPipeline:
    """AgentCard 校验流水线"""

    def __init__(self) -> None:
        self.schema_validator = AgentCardSchemaValidator()
        self.semantic_validator = AgentCardSemanticValidator()

    async def validate(self, agentcard: dict[str, Any], skip_security: bool = False) -> ValidationResult:
        """执行完整校验流水线"""

        result = ValidationResult()

        # Stage 1: Schema 校验
        logger.info("validation_pipeline_start", stage="schema")
        result.schema_errors = self.schema_validator.validate(agentcard)
        if result.schema_errors:
            result.valid = False
            logger.warning("schema_validation_failed", error_count=len(result.schema_errors))
            return result  # Schema 不过则不继续

        # Stage 2: 语义校验
        logger.info("validation_pipeline_continue", stage="semantic")
        result.semantic_errors = self.semantic_validator.validate(agentcard)
        if any(e.severity == "error" for e in result.semantic_errors):
            result.valid = False
            logger.warning("semantic_validation_failed", error_count=len(result.semantic_errors))
            return result

        # Stage 3: 安全扫描（仅技能类，且非跳过模式）
        item_type = agentcard.get("identity", {}).get("item_type")
        if item_type == "skill" and not skip_security:
            logger.info("validation_pipeline_continue", stage="security_scan")
            result.security_scan_result, result.security_scan_details = await self._run_security_scan(agentcard)
            if result.security_scan_result == "failed":
                result.valid = False
                logger.warning("security_scan_failed")
                return result

        logger.info("validation_pipeline_complete", valid=result.valid)
        return result
```

## 一、审计日志写入器

```python
# src/aimart/audit/logger.py

from __future__ import annotations

import hashlib
import json
import time
from datetime import datetime, timezone
from typing import Any
from uuid import uuid4

import structlog

logger = structlog.get_logger()


class AuditLogger:
    """审计日志写入器——所有域的操作都通过此写入器记录日志"""

    def __init__(self, clickhouse_client, kafka_producer) -> None:
        self._ch = clickhouse_client
        self._kafka = kafka_producer
        self._last_hash: dict[str, str] = {}  # 按日志类别维护最后一条的 hash

    async def log(
        self,
        log_type: str,
        actor_type: str,
        actor_id: str,
        target_type: str | None = None,
        target_id: str | None = None,
        action: str = "",
        result: str = "success",
        error_code: str | None = None,
        error_message: str | None = None,
        data: dict[str, Any] | None = None,
        session_id: str | None = None,
        trace_id: str | None = None,
        ip_address: str | None = None,
    ) -> str:
        """
        写入一条审计日志。

        返回：log_id
        """

        # 1. 生成日志条目
        log_id = str(uuid4())
        timestamp = datetime.now(timezone.utc).isoformat()
        category = log_type.split("-")[1] if "-" in log_type else "SY"

        # 2. 计算数据 hash
        data_str = json.dumps(data or {}, sort_keys=True, ensure_ascii=False)
        data_hash = hashlib.sha256(data_str.encode()).hexdigest()

        # 3. 获取前一条日志的 hash（构建哈希链）
        previous_hash = self._last_hash.get(category, "0" * 64)

        # 4. 计算当前条目的 hash
        hash_payload = f"{log_id}|{timestamp}|{actor_id}|{action}|{data_hash}|{previous_hash}"
        current_hash = hashlib.sha256(hash_payload.encode()).hexdigest()

        # 5. 更新 last_hash
        self._last_hash[category] = current_hash

        # 6. 构建完整日志条目
        entry = {
            "log_id": log_id,
            "log_type": log_type,
            "timestamp": timestamp,
            "trace_id": trace_id or str(uuid4()),
            "span_id": str(uuid4()),
            "previous_hash": previous_hash,
            "current_hash": current_hash,
            "actor_type": actor_type,
            "actor_id": actor_id,
            "session_id": session_id,
            "action_operation": action,
            "action_target_type": target_type,
            "action_target_id": target_id,
            "action_result": result,
            "action_error_code": error_code,
            "action_error_message": error_message,
            "data_hash": data_hash,
            "data": data_str,
            "context_ip_hash": hashlib.sha256(ip_address.encode()).hexdigest() if ip_address else None,
        }

        # 7. 异步写入 Kafka（用于实时消费）和 ClickHouse（用于持久化查询）
        await self._write_to_kafka(entry)
        await self._write_to_clickhouse(entry)

        logger.debug(
            "audit_log_written",
            log_id=log_id,
            log_type=log_type,
            actor_id=actor_id,
            action=action,
            result=result,
        )

        return log_id

    async def _write_to_kafka(self, entry: dict) -> None:
        """写入 Kafka 供实时消费"""
        try:
            topic = f"aimart.audit_{entry['log_type'].split('-')[1].lower() if '-' in entry['log_type'] else 'sy'}"
            await self._kafka.produce(
                topic=topic,
                key=entry["log_id"],
                value=json.dumps(entry, ensure_ascii=False).encode(),
            )
        except Exception as e:
            logger.error("audit_kafka_write_failed", error=str(e), log_id=entry.get("log_id"))

    async def _write_to_clickhouse(self, entry: dict) -> None:
        """写入 ClickHouse 供持久化查询"""
        try:
            await self._ch.execute(
```

## 二、哈希链校验

```python
# src/aimart/audit/hashchain.py

from __future__ import annotations

import hashlib
import json
from typing import Any

import structlog

logger = structlog.get_logger()


class HashChainVerifier:
    """审计日志哈希链校验器"""

    @staticmethod
    def compute_hash(entry: dict[str, Any]) -> str:
        """计算单条日志条目的 hash"""
        payload = (
            f"{entry['log_id']}"
            f"|{entry['timestamp']}"
            f"|{entry['actor_id']}"
            f"|{entry['action_operation']}"
            f"|{entry['data_hash']}"
            f"|{entry['previous_hash']}"
        )
        return hashlib.sha256(payload.encode()).hexdigest()

    @classmethod
    def verify_chain(cls, entries: list[dict[str, Any]]) -> dict[str, Any]:
        """
        验证日志链完整性。

        返回：
        {
            "verified": bool,
            "total_checked": int,
            "broken_at": str | None,  # 断裂处的 log_id
            "broken_at_index": int | None,
        }
        """
        if not entries:
            return {"verified": True, "total_checked": 0, "broken_at": None, "broken_at_index": None}

        # 按 timestamp 排序
        sorted_entries = sorted(entries, key=lambda e: e["timestamp"])

        broken_at = None
        broken_at_index = None

        for i in range(1, len(sorted_entries)):
            prev = sorted_entries[i - 1]
            curr = sorted_entries[i]

            # 计算 prev 的 hash
            expected_hash = cls.compute_hash(prev)

            # 检查 curr 的 previous_hash 是否等于 prev 的计算 hash
            if curr["previous_hash"] != expected_hash:
                broken_at = curr["log_id"]
                broken_at_index = i
                logger.warning(
                    "hash_chain_broken",
                    at_log_id=curr["log_id"],
                    expected_previous_hash=expected_hash,
                    actual_previous_hash=curr["previous_hash"],
                )
                break

        verified = broken_at is None
        return {
            "verified": verified,
            "total_checked": len(sorted_entries),
            "broken_at": broken_at,
            "broken_at_index": broken_at_index,
        }

    @classmethod
    def verify_single(cls, entry: dict[str, Any], previous_entry: dict[str, Any] | None) -> bool:
        """验证单条日志与前一条的链接"""
        if previous_entry is None:
            return True  # 链首无前驱

        expected_hash = cls.compute_hash(previous_entry)
        return entry["previous_hash"] == expected_hash


class CheckpointGenerator:
    """哈希链检查点生成器——每 N 条日志生成一个检查点"""

    CHECKPOINT_INTERVAL = 10000

    @classmethod
    def generate(cls, entries: list[dict[str, Any]], date: str) -> dict[str, Any]:
        """生成一个检查点"""
        if not entries:
            return {
                "date": date,
                "entry_count": 0,
                "first_log_id": None,
                "last_log_id": None,
                "merkle_root": hashlib.sha256(b"empty").hexdigest(),
            }

        sorted_entries = sorted(entries, key=lambda e: e["timestamp"])

        # 计算 Merkle Root
        merkle_root = cls._compute_merkle_root([e["current_hash"] for e in sorted_entries])

        return {
            "date": date,
            "entry_count": len(sorted_entries),
            "first_log_id": sorted_entries[0]["log_id"],
            "last_log_id": sorted_entries[-1]["log_id"],
            "first_timestamp": sorted_entries[0]["timestamp"],
            "last_timestamp": sorted_entries[-1]["timestamp"],
            "merkle_root": merkle_root,
        }

    @staticmethod
    def _compute_merkle_root(hashes: list[str]) -> str:
        """计算 Merkle Root"""
        if not hashes:
            return hashlib.sha256(b"empty").hexdigest()

        if len(hashes) == 1:
            return hashes[0]

        # 成对哈希
        next_level = []
        for i in range(0, len(hashes), 2):
            if i + 1 < len(hashes):
                combined = hashlib.sha256(f"{hashes[i]}|{hashes[i+1]}".encode()).hexdigest()
            else:
                combined = hashes[i]
            next_level.append(combined)

        return CheckpointGenerator._compute_merkle_root(next_level)
```

```python
    """验证 JWT Token"""
    try:
        payload = jwt.decode(
            token,
            settings.security_jwt_public_key,
            algorithms=[settings.security_jwt_algorithm],
            issuer=settings.security_jwt_issuer,
        )
        participant_id = payload.get("sub")
        participant_type = payload.get("type")
        agent_id = payload.get("agent_id")
        if participant_id is None:
            raise HTTPException(status_code=401, detail="Invalid token")
        return AuthContext(participant_id, participant_type, agent_id)
    except JWTError:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
```
